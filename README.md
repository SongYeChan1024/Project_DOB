## 1. 저장소 구조

저장소 루트가 곧 Unity 프로젝트이고, 문서는 `Docs/`에 둡니다.

```text
Project_DOB/
├─ Assets/
│  └─ _DOB/                 우리 게임 에셋 (외부 에셋과 섞이지 않게 분리)
│     ├─ 01.Scenes/
│     ├─ 02.Scripts/        Data · Game · UI (6장)
│     ├─ 03.Prefabs/        완성품 프리팹 — 씬에는 이것만 배치 (4장)
│     ├─ 04.Art/            Models · Textures · Materials · VFX
│     ├─ 05.Animations/
│     ├─ 06.Audio/          BGM · SFX
│     ├─ 07.UI/
│     ├─ 08.Data/           ScriptableObject 데이터 (몬스터·재료·요리·종족·경제)
│     ├─ 99.ThirdParty/     외부 에셋 — Git에 올리지 않음, 설치 목록으로 공유 (5장)
│     ├─ Resources/         이름으로 불러와야 하는 것만 (거의 없음)
│     └─ _Local/            개인 실험용 — Git에 올라가지 않음
├─ Packages/
├─ ProjectSettings/
├─ Docs/                    명세 · 데이터 표 · 회의록 · 플레이 테스트 기록
├─ .github/                 PR 템플릿
├─ README.md                팀 규칙 (이 문서)
└─ CLAUDE.md                Claude 작업 안내 (이 README를 따르도록 연결)
```

- Unity는 `Assets` 밖의 폴더를 읽지 않으므로 `Docs/`가 빌드에 들어가지 않습니다.
- `Library/`, `Temp/`, `Logs/`, `UserSettings/`, IDE 파일은 `.gitignore`로 제외합니다. PC마다 다시 만들어지므로 처음 열 때 오래 걸리는 것은 정상입니다.

## 3. Git 규칙

### 브랜치 — main을 가운데에 두고 feature · fix

```text
feature/이름-기능 ──PR──▶ main ◀──PR── fix/이름-버그
```

| 브랜치 | 용도 | 예 |
| --- | --- | --- |
| `main` | 항상 **플레이 가능한 상태**. 직접 push 금지, PR로만 | — |
| `feature/이름-기능` | 새 기능 | `feature/yechan-menu-resolver` |
| `fix/이름-버그` | 버그 수정 | `fix/yechan-tie-break` |

- 브랜치는 항상 최신 `main`에서 만들고, 끝나면 `main`으로 PR을 엽니다. 병합한 브랜치는 지웁니다.
- 내 브랜치를 최신으로 맞출 때만 `main` → 내 브랜치를 허용합니다. **다른 사람 브랜치끼리는 섞지 않습니다.**
- 브랜치 이름에 `#`, 공백, 한글을 쓰지 않습니다.
- 마일스톤마다 `main`에 태그를 붙입니다: `v0.1-alpha`(6일차) · `v0.2-test`(7일차) · `v1.0`(11일차). 문제가 생기면 태그 시점으로 돌아가 빌드합니다.
- 💡 병합은 **하루 2번 정해진 시간**에 몰아서 합니다 (🔴 시간 정하기). 오래 쌓인 PR일수록 충돌이 커집니다.

### 커밋 메시지

```text
타입(분야): 무엇을 했는지 한 줄

- 왜 / 무엇을 바꿨는지 불릿으로
```

| 타입 | 언제 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 같고 구조 개선 |
| `asset` | 모델·텍스처·사운드 추가·교체 |
| `docs` | 문서 |
| `chore` | 설정·패키지·그 외 |

분야: `사냥` · `경영` · `UI` · `아트` · `사운드` · `기획` · `공통`

예: `feat(사냥): 재료 근접 자동 습득 추가` / `fix(경영): 메뉴 결정 동률 처리 수정`

- 타입은 소문자, 콜론 뒤 한 칸. `Feat:`, `fix :`, 타입 없는 제목은 쓰지 않습니다.

### PR

- PR 하나에 기능 하나. 본문은 템플릿(무엇을 / 왜 / 바꾼 씬·프리팹 / 확인 방법)을 채웁니다.
- **리뷰어 1명**이 확인한 뒤 병합합니다. 씬이나 핵심 프리팹을 바꿨으면 그 담당자가 리뷰합니다.
- PR은 **그날 안에** 처리합니다.

### 매일 지킬 순서

1. Unity를 열기 **전에** `git pull`
2. 작업 → Unity에서 저장
3. 커밋 → `git push` (작업 중이어도 그날 끝날 때는 자기 브랜치에 push)

- 에셋을 추가·이동·삭제하면 **`.meta` 파일도 함께** 커밋합니다. `.meta`가 빠지면 다른 사람 PC에서 참조가 끊깁니다.

## 4. 씬·프리팹 담당 규칙

**씬과 핵심 프리팹은 담당자 1명만 수정합니다.** 다른 사람은 자기 프리팹을 만들어 PR로 전달하고, 배치는 담당자가 합니다.

| 대상 | 담당 |
| --- | --- |
| `Title` 씬 | 🔴 |
| `Dungeon` (사냥) 씬 | 🔴 |
| `Restaurant` (영업) 씬 | 🔴 |
| `Result` (정산·결과) 씬 | 🔴 |
| `PF_Player` | 🔴 |
| `PF_GameManager` (날짜·골드·상태) | 🔴 |
| 공용 UI Canvas 프리팹 | 🔴 |

- 실험은 `Assets/_DOB/_Local/`의 개인 씬에서 합니다.
- 백업 씬(`... BackUp.unity`, `_old`)이나 `_Deprecated` 폴더는 만들지 않습니다. 지난 버전은 Git 기록에서 찾습니다.
- 충돌이 나면 혼자 덮어쓰지 말고 담당자와 같이 해결합니다.

### 완성품 프리팹

씬에는 **완성품 프리팹만** 배치합니다. 외부 에셋 모델이나 `04.Art`의 원본 모델을 씬에 바로 끌어다 놓지 않습니다.

```text
99.ThirdParty / 04.Art 의 모델·텍스처        (재료)
        ↓ 프리팹으로 옮기기
03.Prefabs/PF_이름                           (완성품)
  = 모델 + 콜라이더·애니메이터 등 컴포넌트
  + 우리 스크립트 + 인스펙터 연결 + 08.Data의 ScriptableObject 연결
        ↓
01.Scenes                                    (배치만)
```

**완성품 체크리스트** — PR 올리기 전에 확인합니다.

- [ ] `03.Prefabs/분류/PF_이름` 위치에 있다 (분류: `Characters` · `Monsters` · `Props` · `UI` · `Systems`)
- [ ] 필요한 스크립트가 붙어 있고, **인스펙터의 참조 칸이 비어 있지 않다** (Missing·None 없음)
- [ ] 수치는 `08.Data`의 ScriptableObject를 연결해서 쓴다 (프리팹에 숫자를 직접 입력하지 않음)
- [ ] 빈 씬에 하나만 놓고 Play 해도 혼자 동작한다 (다른 씬 오브젝트를 찾지 않음)
- [ ] 외부 에셋을 썼다면 5장 「외부 에셋 설치 목록」에 적혀 있다

- 비슷한 것이 여러 개면 **기본 프리팹 + 프리팹 배리언트**로 만듭니다. 예: `PF_Monster_Base` → `PF_Monster_Cabbage` · `PF_Monster_Mushroom` · `PF_Monster_Carrot`. 공통 수정은 기본 프리팹에서 한 번만 합니다.
- 완성품 프리팹의 담당은 그 기능을 만든 사람입니다. 위 담당표의 핵심 프리팹은 담당자만 수정합니다.

## 5. 에셋 규칙 (Git LFS 없음)

### 어디에 두나

| 구분 | 위치 | Git | 무엇 |
| --- | --- | --- | --- |
| 공유 에셋 | `Assets/_DOB/04.Art`, `06.Audio` … | ✅ | 게임에 들어가는 모든 것 |
| Resources | `Assets/_DOB/Resources/` | ✅ | 코드에서 이름으로 불러와야 하는 것만 |
| 외부 에셋 | `Assets/_DOB/99.ThirdParty/` | ❌ | Asset Store 등 외부 에셋. **설치 목록으로 공유** |
| 개인 폴더 | `Assets/_DOB/_Local/` | ❌ | 테스트 씬·시험 에셋. **게임에서 참조 금지** |
| 원본 | 공유 드라이브 🔴 | ❌ | `.psd`, `.blend`, `.wav` 원본 등 작업 파일 |

- **판단 기준:** "이 파일을 게임이 쓰나?" 쓰면 공유 에셋에 두고, 크면 숨기지 말고 **줄입니다.**

### 외부 에셋은 Git에 올리지 않는다

- 이유 1 — **용량:** 에셋 팩은 쓰지 않는 파일까지 수백 MB가 됩니다.
- 이유 2 — **라이선스:** 이 저장소는 공개 저장소입니다. Asset Store 에셋 원본을 공개 저장소에 올리면 재배포가 될 수 있습니다.
- 대신 아래 **설치 목록**으로 공유합니다. 같은 패키지·같은 버전을 같은 위치에 임포트하면 Unity가 같은 GUID를 쓰므로, 우리 프리팹의 참조가 그대로 이어집니다.

규칙

- 새 외부 에셋을 넣는 사람은 **같은 PR에서 설치 목록에 한 줄 추가**합니다. 다른 팀원은 그 PR을 받은 뒤 Package Manager → **My Assets**에서 같은 에셋을 임포트합니다.
- 임포트 창에서 **필요한 폴더만** 체크합니다(데모 씬 제외). 무엇을 뺐는지 비고에 적습니다.
- `99.ThirdParty` 안의 파일은 **고치지 않습니다.** 고친 내용은 다른 사람에게 가지 않습니다. 바꾸려면 `04.Art`로 복사해서 고칩니다(복사본은 Git에 올라감).
- `Assets/패키지명/`처럼 자기 위치에 설치되는 패키지는 옮기지 않고, 그 폴더를 `.gitignore`의 「외부 에셋」 칸에 추가합니다.
- 재배포가 허용된 CC0 에셋(예: Kenney)과 팀이 직접 만든 에셋은 `04.Art`에 넣고 Git에 올립니다.
- 크기 규칙(아래)은 `_DOB/`의 우리 에셋에 적용합니다.

### 크기

| 종류 | 규칙 |
| --- | --- |
| 파일 하나 | 💡 **20MB 이하** (GitHub 한도는 100MB) |
| 텍스처 | 💡 2048px 이하 |

| 한글 폰트 | 쓰는 글자만 담은 TMP 폰트 에셋 |

| 종류 | 접두사 | 예 |
| --- | --- | --- |
| 모델 | `SM_` | `SM_Monster_Cabbage` |
| 텍스처 | `T_` | `T_Monster_Cabbage_Albedo` |

## 6. 코드 규칙

### 구조 — 3계층 💡

```text
UI    (화면 표시와 입력)
 │ 참조
Game  (사냥 · 메뉴 결정 · 영업 · 경제 · GameManager)
 │ 참조
Data  (ScriptableObject 정의 · enum · 데이터 클래스)
```

- 위 계층은 아래 계층을 참조할 수 있고, **아래 계층은 위를 참조하지 않습니다.** `Game`은 `UI`를 모릅니다. 화면을 바꿔야 하면 이벤트를 내보내고 `UI`가 받습니다.
- `UI`는 표시와 입력만 합니다. 게임 규칙(계산·판정)을 `UI`에 쓰지 않습니다.
- `FindObjectOfType` 같은 `Find*` 계열은 쓰지 않고, 인스펙터 연결이나 `GameManager`를 통해 찾습니다.
- 💡 계층마다 asmdef를 두면 Unity가 역참조를 컴파일 오류로 막아 줍니다. 1일차 세팅 때 넣을지 결정합니다.

### 이름

- 클래스·메서드·프로퍼티: `PascalCase`
- private 필드: `camelCase` 💡 (`_` 접두사는 쓰지 않음)
- 인스펙터 노출은 `public` 필드 대신 `[SerializeField] private`
- 파일 하나에 `MonoBehaviour` 클래스 하나, 파일 이름과 클래스 이름을 같게

### 수치는 코드에 쓰지 않는다

몬스터 체력, 요리 가격, 보너스 같은 **기획 수치는 `08.Data`의 ScriptableObject**로 만듭니다. `Docs/`의 데이터 표와 1:1로 맞춰서, 수치를 바꿀 때 코드를 고치지 않게 합니다.

### 주석

| 종류 | 어디에 | 무엇을 |
| --- | --- | --- |
| 파일 헤더 | 파일 맨 위 | 역할 · 누가 호출하나 · 무엇을 호출하나 · 가진 상태 |
| `/// <summary>` | 공개 멤버, `[SerializeField]` 필드 | 무엇인지, 단위·범위 (값은 쓰지 않음) |
| 의사코드 | 흐름이 복잡한 함수만 | 처리 순서를 3~6단계로 요약 |
| "왜" 주석 | 해당 줄 위 한 줄 | 매직 넘버, 설계 결정의 이유 |

- 코드를 그대로 옮긴 문장, 값을 반복하는 주석(`이동속도 = 5`)은 쓰지 않습니다.
- **코드를 고친 커밋에서 주석도 같이 고칩니다.**

## 7. 기획 · 문서 규칙

### 규칙은 두 층으로 쓴다

| 층 | 누구를 위한 것 | 형태 |
| --- | --- | --- |
| 플레이어 규칙 | 플레이어 | 한 문장, 수치·공식 없음 |
| 시스템 규칙 | 기획·프로그래밍 | 공식, 기준값, 동률·예외 처리 |

- 시스템 규칙은 플레이어 규칙을 **배신하지 않아야** 합니다. 플레이어 규칙대로 플레이한 사람이 가장 이득이어야 합니다.
- 공식은 숨기고 결과는 보여줍니다. 시스템 규칙마다 **"플레이어가 이걸 어떤 화면·연출로 아는가"** 를 함께 적습니다.
- 예외는 기본적으로 "아무 일도 안 일어나는" 쪽으로 정합니다.

### 문서는 어디에

| 무엇 | 기준 |
| --- | --- |
| 팀 규칙 | 이 README |
| 시스템 명세 · 데이터 표 · 밸런스 | `Docs/` |
| GDD 개요 · 일정 보드 · 회의 메모 | 노션 (필요하면 `Docs/`에서 링크) |

- 💡 `Docs/`와 노션 내용이 다르면 `Docs/`를 따릅니다. 🔴 팀 확정
- 문서 버전은 **Git으로 관리**합니다. `_v1.2.md`처럼 파일을 복사해 남기지 않습니다.
- 규칙·수치를 바꾸면 **문서를 먼저** 고치고 변경 기록을 남긴 뒤 구현합니다. 테스트 전 수치는 💡 가안으로 표시합니다.

### 시스템 명세 목차

`0 기획 의도 → 1 플레이어 규칙 → 2 시스템 규칙(트리거·순서·예외) → 3 데이터 → 4 UI·피드백 → 변경 기록`

데이터 표 형식: `기획 명칭 | 변수명 | 타입 | 초기값 | 비고`
