## 1. 저장소 구조

문서는 `Docs/`, 기존 웹 시제품은 `Prototypes/Web/`에 둡니다.
현재 체크아웃에는 Unity 프로젝트의 Assets·Packages·ProjectSettings가 없으며, 아래 구조는 Unity 세팅 시 사용할 목표 구조입니다.

```text
Project_DOB/
├─ Assets/
│  └─ _DOB/                 우리 게임 에셋 (외부 에셋과 섞이지 않게 분리)
│     ├─ 01.Scenes/
│     ├─ 02.Scripts/        Define · Utils · System · UI · Manager · Presenter (6장)
│     ├─ 03.Prefabs/
│     ├─ 04.Art/            Models · Textures · Materials · VFX
│     ├─ 05.Animations/
│     ├─ 06.Audio/          BGM · SFX
│     ├─ 07.UI/
│     ├─ 08.Data/           ScriptableObject 데이터 (층·재료·요리·종족·경제)
│     ├─ 99.ThirdParty/     외부 에셋 (Git에 올림)
│     ├─ Resources/         이름으로 불러와야 하는 것만 (거의 없음)
│     └─ _Local/            개인 실험용 — Git에 올라가지 않음
├─ Packages/
├─ ProjectSettings/
├─ Docs/                    명세 · 데이터 표 · 회의록 · 플레이 테스트 기록
├─ .github/                 PR 템플릿
├─ README.md                팀 규칙 (이 문서)
└─ CLAUDE.md                Claude 작업 안내 (이 README를 따르도록 연결)
```

- Unity는 `Assets` 밖의 폴더를 읽지 않으므로 `Docs/`가 빌드에 들어가지 않습니다.
- `Library/`, `Temp/`, `Logs/`, `UserSettings/`, IDE 파일은 `.gitignore`로 제외합니다. PC마다 다시 만들어지므로 처음 열 때 오래 걸리는 것은 정상입니다.

## 3. Git 규칙

### 브랜치 — main을 가운데에 두고 feature · fix

```text
feature/이름-기능 ──PR──▶ main ◀──PR── fix/이름-버그
합의된 문서만 변경 ──직접 커밋·push──▶ main
```

| 브랜치 | 용도 | 예 |
| --- | --- | --- |
| `main` | 통합 기준. 코드·에셋·설정은 PR, 합의된 문서만 변경할 때는 직접 커밋·push 허용 | — |
| `feature/이름-기능` | 새 기능 | `feature/yechan-menu-resolver` |
| `fix/이름-버그` | 버그 수정 | `fix/yechan-tie-break` |

- 코드·에셋·설정 작업은 최신 `main`에서 브랜치를 만들고, 끝나면 `main`으로 PR을 엽니다. 병합한 브랜치는 지웁니다.
- 내 브랜치를 최신으로 맞출 때만 `main` → 내 브랜치를 허용합니다. **다른 사람 브랜치끼리는 섞지 않습니다.**
- 브랜치 이름에 `#`, 공백, 한글을 쓰지 않습니다.
- 마일스톤마다 `main`에 태그를 붙입니다: `v0.1-alpha` · `v0.2-test` · `v1.0`. 날짜는 제작 검증 후 정합니다. 문제가 생기면 태그 시점으로 돌아가 빌드합니다.
- 💡 병합은 **하루 2번 정해진 시간**에 몰아서 합니다 (🔴 시간 정하기). 오래 쌓인 PR일수록 충돌이 커집니다.

### 문서 변경과 구현 변경 구분

| 변경 내용 | 커밋·push 경로 | 확인 |
| --- | --- | --- |
| 팀과 합의한 README·Docs 문서의 작성·수정 | main에 직접 커밋·push 가능. 별도 PR·추가 리뷰 불필요 | 원문·링크·변경 기록과 포함 파일 확인 |
| 저장소 작업 안내·PR 설명 템플릿의 문구 정리 | 합의된 문서 변경과 동일 | README와 규칙 일치 확인 |
| 코드·씬·프리팹·게임 에셋·패키지·프로젝트 설정·CI/배포 설정 | 작업 브랜치 → PR → 리뷰 후 main 병합 | 담당 리뷰와 해당 실행 검증 |
| 문서와 구현을 함께 변경 | 구현 PR에 문서 포함 | 구현과 문서의 일치 확인 |

문서 반영은 이미 논의한 내용을 기록하는 과정입니다. 합의하지 않은 새 규칙·수치를 확정된 것으로 올리지 않고 제안·검토 표시를 유지합니다.
문서 폴더 안에 있거나 커밋 타입이 docs라는 이유만으로 실행 코드·설정 변경에 문서 예외를 적용하지 않습니다.
보호 규칙으로 직접 push가 차단되면 강제 push나 보호 해제 없이 기존 PR 경로를 사용합니다.

### 커밋 메시지

```text
타입(분야): 무엇을 했는지 한 줄

- 왜 / 무엇을 바꿨는지 불릿으로
```

| 타입 | 언제 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 같고 구조 개선 |
| `asset` | 모델·텍스처·사운드 추가·교체 |
| `docs` | 문서 |
| `chore` | 설정·패키지·그 외 |

분야: `경영` · `조리` · `손님` · `UI` · `아트` · `사운드` · `기획` · `공통`

예: `feat(조리): 재료 직접 투입 추가` / `fix(경영): 메뉴 결정 동률 처리 수정`

- 타입은 소문자, 콜론 뒤 한 칸. `Feat:`, `fix :`, 타입 없는 제목은 쓰지 않습니다.

### 커밋·push 전후 확인

1. 현재 브랜치와 `git status`를 확인하고, 다른 사람이나 다른 작업의 변경을 섞지 않습니다.
2. 문서 직접 반영은 main에서 `git pull --ff-only`로 최신 내용을 받은 뒤 수정합니다. 변경 기록에 작성자·날짜·내용을 남깁니다.
3. `git diff`와 링크·내용을 확인하고, 올릴 파일 경로만 골라 stage합니다.
4. `git diff --cached`와 `git diff --cached --check`로 실제 커밋 대상을 확인합니다.
5. 한 목적 단위로 커밋합니다. 문서만 변경하면 `docs(기획): ...` 또는 `docs(공통): ...`를 사용합니다.
6. 문서 직접 반영은 `git push origin main`, 구현은 자기 작업 브랜치에 push한 뒤 PR을 엽니다.
7. push 결과와 로컬·원격 커밋 일치를 확인하고 작업 카드에 커밋 또는 PR을 연결합니다.

원격이 앞서 push가 거절되면 변경을 보존하고 최신 내용을 통합한 뒤 다시 검증합니다. 공용 브랜치에 강제 push하지 않습니다.

### PR

아래 리뷰 절차는 코드·에셋·설정 변경에 적용합니다. 합의된 문서만 반영하는 작업에는 별도 PR을 요구하지 않습니다.

- PR 하나에 기능 하나. 본문은 템플릿(무엇을 / 왜 / 바꾼 씬·프리팹 / 확인 방법)을 채웁니다.
- 작성자 외 **리뷰어 1명**이 확인한 뒤 병합합니다. 씬이나 핵심 프리팹을 바꿨으면 해당 담당자의 확인도 받습니다.
- 로직·통합 변경은 김언호, UI·화면 연결 변경은 홍준우가 해당 책임 범위를 확인합니다. 개발자 자신의 변경은 다른 개발자가 검토합니다.
- 기획·수치·원고는 송예찬, 아트·연출은 이기혁이 내용 확인을 맡고, 실행에 연결되는 변경은 해당 개발자가 함께 확인합니다.
- 기술 통합과 실행 빌드 확인은 김언호가 맡습니다. 화면 연결은 홍준우와 함께, 플레이 기준 충족은 송예찬과 함께 확인합니다.
- PR은 그날 검토하는 것을 원칙으로 하되, 리뷰·완료 기준을 건너뛰어 병합하지 않습니다. 보류 사유와 다음 확인 시점을 남깁니다.

### 매일 지킬 순서

1. Unity를 열기 **전에** 현재 브랜치와 변경 파일을 확인하고 `git pull --ff-only`
2. 작업 카드의 범위·완료 기준과 수정할 공용 파일 담당을 확인
3. 작업 → Unity에서 저장 → 변경 파일·참조·실행 결과 확인
4. 문서만 변경하면 main에 커밋·push, 구현은 자기 브랜치에 push → PR과 확인 결과 연결
5. 하루 종료 시 진행 상태·남은 문제·다음 작업을 작업 카드에 기록

로컬 변경 때문에 pull이 중단되면 덮어쓰지 않고 변경을 보존한 뒤 해결합니다. 진행 중인 구현은 자기 브랜치에 보관하며 완료 전에는 main에 병합하지 않습니다.

- 에셋을 추가·이동·삭제하면 **`.meta` 파일도 함께** 커밋합니다. `.meta`가 빠지면 다른 사람 PC에서 참조가 끊깁니다.

하루 전환·저장 데이터 계약은 김언호와 홍준우가 함께 정합니다. 상태 변경·저장 복구·기술 통합은 김언호, 해당 입력·표시·화면 전환은 홍준우가 맡습니다.
송예찬은 기획상의 경계와 기대 결과를 확인하고, 이기혁은 화면에 필요한 아트 리소스를 제공합니다.

### 씬·프리팹 공동 작업

**씬과 핵심 프리팹은 담당자 1명만 수정합니다.** 다른 사람은 자기 프리팹을 만들어 PR로 전달하고, 배치는 담당자가 합니다.

| 대상·작업 범위 | 담당 |
| --- | --- |
| 타이틀·준비·귀환 보고의 화면과 UI 프리팹 | 홍준우 |
| 식당의 이동·상호작용·손님/주방 연결과 실행 씬 통합 | 김언호 |
| 식당·자리 소품·캐릭터의 아트 에셋과 외형 프리팹 | 이기혁 |
| 플레이어 기능 프리팹, 하루 진행·저장 연결 오브젝트 | 김언호 |
| 공용 UI Canvas·대화·조리·보고·수첩 View/Presenter | 홍준우 |
| 기획 데이터·대사·플레이 테스트 기록 | 송예찬 |

위 항목은 역할별 수정 범위이며 새 씬·프리팹 이름을 강제하지 않습니다. `Title`·`Result` 등의 기존 이름은 구조 예시입니다.
하나의 실행 씬에 로직·UI·아트가 함께 들어가면 김언호가 통합하고, 각 담당자는 자기 프리팹·리소스를 전달합니다.
같은 `.unity`·`.prefab` 파일은 동시에 편집하지 않습니다. 작업 카드에 실제 경로와 현재 편집자를 남기고 인계 후 다음 사람이 수정합니다.

- 실험은 `Assets/_DOB/_Local/`의 개인 씬에서 합니다.
- 백업 씬(`... BackUp.unity`, `_old`)이나 `_Deprecated` 폴더는 만들지 않습니다. 지난 버전은 Git 기록에서 찾습니다.

## 6. 코드 규칙

### 구조 — 5계층 💡

기존 5계층 제안을 역할과 허용 참조로 설명합니다. 아래 계층은 위 계층을 참조하지 않고, UI와 System은 서로 직접 참조하지 않습니다. Manager·Presenter가 필요한 하위 계층을 조립합니다. asmdef 적용 여부는 아래 검토 항목을 따릅니다.

```text
[4] Manager · Presenter   하위 계층을 조립하고 UI와 System 사이를 잇는다   → 0 · 1 · 2 · 3 참조
[3] UI                    화면 표시와 입력만. 계산 없이 이벤트를 보낸다     → 0 · 1 참조
[2] System                게임 규칙 · 판정 · 상태 머신                       → 0 · 1 참조
[1] Utils                 공용 도구 · 확장 메서드 · 이벤트 버스             → 0 참조
[0] Define                ScriptableObject 정의 · enum · 데이터 클래스       → 참조 없음
```

| 계층 | 폴더 (`02.Scripts/`) | 하는 일 | 예 |
| --- | --- | --- | --- |
| 0 Define | `Define/` | 데이터의 모양만 정의한다. 로직 없음 | 위험 축 enum, 레시피 · 층 · 손님 데이터 클래스 |
| 1 Utils | `Utils/` | 어디서나 쓰는 도구와 전역 이벤트 버스 | `EventBus`, 난수 · 수학 도우미 |
| 2 System | `System/` | 게임 규칙·판정·상태 전이. 화면을 참조하지 않음 | 위험 판정, 손님 흐름, 조리 타이머, 정산 |
| 3 UI | `UI/` | 화면 표시와 입력. 계산 · 판정을 하지 않음 | 대화창, 주방 카운터, 귀환 보고 화면 |
| 4 Manager · Presenter | `Manager/`, `Presenter/` | 하위 계층을 조립하고 중재, 씬과 하루 진행 | `GameManager`, 화면별 Presenter |

- **아래 계층은 위를 참조하지 않습니다.** 독립 기능 사이의 알림은 이벤트 또는 Presenter 중재를 사용합니다. 같은 기능 내부의 계산·조회까지 전역 이벤트로 바꾸지 않습니다.
- **UI는 System을 모릅니다.** 입력은 이벤트로 보내고, System의 결과를 화면에 옮기는 일은 Presenter가 합니다. UI 담당과 로직 담당이 서로의 파일을 고치지 않아도 됩니다.
- 판정 · 계산 같은 게임 규칙은 System에 쓰고, 가능하면 `MonoBehaviour`가 아닌 순수 C# 클래스로 만듭니다. 테스트와 화면 미리보기가 같은 코드를 쓰게 하기 위해서입니다.
- `GameManager`는 하루 진행과 기능 연결을 조정합니다. 금화·재고·손님·주문의 실제 변경은 각각의 상태를 소유한 System이 수행합니다. 같은 값을 Manager와 System에 따로 보관하지 않습니다.
- `FindObjectOfType` 같은 `Find*` 계열은 쓰지 않고, 인스펙터 연결이나 Presenter를 통해 받습니다.
- 💡 계층마다 asmdef를 둬서 역참조를 컴파일 오류로 막습니다. 이름은 `DOB.Define` · `DOB.Utils` · `DOB.Systems` · `DOB.UI` · `DOB.Manager`로 둡니다. System 계층만 `Systems`인 이유는 .NET의 `System` 네임스페이스와 겹치지 않게 하기 위해서입니다. 1일차 세팅 때 확정합니다.

### 상태를 바꾸는 곳은 하나

| 상태·처리 | 변경 주체 | 화면의 역할 |
| --- | --- | --- |
| 손님 이름·종족·직업·개인 취약점·호감 | 손님/관계 System · 김언호 | 관찰·수첩·관계 표시 · 홍준우 |
| 방문·주문·재료 소비·조리·접시 소유자 | 주문/조리 System · 김언호 | 조합 요청·진행·완성 표시 · 홍준우 |
| 금화·재고·귀환 보상·보고 처리 ID | 경제/정산 System · 김언호 | 구매·보고 확인 요청과 결과 표시 · 홍준우 |
| 하루 단계·영업/조리 시계·정지 사유 | 하루 진행 System과 연결 Manager · 김언호 | 화면 열기/닫기 알림 · 홍준우 |
| 저장·복구·난수·필수 사실·중복 처리 | 저장 연결 · 김언호, 데이터 계약은 홍준우와 공동 | 재개·오류·저장 결과 표시 · 홍준우 |
| 규칙·기준값·대사 원고 | 기획 데이터 작성 · 송예찬, 로딩/검증 연결 · 김언호 | 같은 원본으로 미리보기·결과 표시 |

UI는 금화·재고·호감을 직접 수정하거나 조리 완료·귀환 등급을 자체 계산하지 않습니다.
Presenter는 입력을 요청으로 옮기고 결과를 표시하며, 게임 규칙을 다시 구현하지 않습니다.
ScriptableObject는 기준 데이터, 실행 중 상태와 저장 데이터는 별도로 관리합니다.
표의 System 명칭은 책임 설명이며 실제 클래스 이름은 구현할 때 맞춥니다.

### 요청·결과·생명주기

- 요청에는 `guestId`·`visitId`·`orderId` 등 필요한 식별자를 넣습니다. 화면 선택 인덱스나 표시 이름을 판정 키로 쓰지 않습니다.
- System은 유효성 검사와 상태 변경을 마친 뒤 성공·거절 사유와 결과를 전달합니다. 같은 주문의 중복 확정·픽업·서빙·정산을 막습니다.
- 미리보기와 최종 판정은 같은 계산기를 사용합니다. UI는 플레이어가 알아낸 정보만 표시합니다.
- 이벤트 구독과 해제의 수명은 짝을 맞춥니다. 화면 재열기·씬 재진입으로 중복 구독하거나 닫힌 화면을 갱신하지 않습니다.
- 초기화·구독·저장 복구 순서는 연결 담당이 명시합니다. `Awake`·`Start`의 우연한 호출 순서에 기대지 않습니다.
- 현재 시간 정책은 [최신 결정](Docs/기획/CurrentDecisions.md)을 따릅니다. 영업과 조리의 시간이 다르게 흐르므로 전체 정지를 한 변수로 처리하지 않습니다.

구체적인 연결 예시와 인계 항목은 [개발 연결·상태 관리 지침](Docs/개발/EngineeringGuide.md)을 따릅니다.

#### 이 구조에서 쓰지 않는 것

| 쓰지 않는 것 | 대신 | 이유 |
| --- | --- | --- |
| 네트워크 동기화 · 서버 DB 계층 | 없음 | 싱글 · 오프라인 게임 |
| master · develop · release · hotfix 브랜치 (git flow) | 3장의 main + feature + fix | 현재 팀 규모와 제작 범위에 불필요한 분기 증가 |
| Excel → JSON 파싱 + Addressables | `08.Data`의 ScriptableObject. 💡 대사 조각처럼 양이 많은 데이터만 시트 → JSON을 검토 | 레시피 · 층 데이터가 적음 |
| `_Deprecated` 폴더 | 쓰지 않음 (4장) | 지난 버전은 Git 기록에서 찾음 |

### 이름

- 클래스·메서드·프로퍼티: `PascalCase`
- private 필드: `camelCase` 💡 (`_` 접두사는 쓰지 않음)
- 인스펙터 노출은 `public` 필드 대신 `[SerializeField] private`
- 파일 하나에 `MonoBehaviour` 클래스 하나, 파일 이름과 클래스 이름을 같게

### 수치는 코드에 쓰지 않는다

층 위험, 요리 가격, 조리 시간, 취약점 확률 같은 **기획 수치는 `08.Data`의 ScriptableObject**로 만듭니다. 최신 노션·`Docs/`의 데이터 표와 맞춰 수치를 바꿀 때 코드를 고치지 않게 합니다.

### 주석

| 종류 | 어디에 | 무엇을 |
| --- | --- | --- |
| 파일 헤더 | 파일 맨 위 | 역할 · 누가 호출하나 · 무엇을 호출하나 · 가진 상태 |
| `/// <summary>` | 공개 멤버, `[SerializeField]` 필드 | 무엇인지, 단위·범위 (값은 쓰지 않음) |
| 의사코드 | 흐름이 복잡한 함수만 | 처리 순서를 3~6단계로 요약 |
| "왜" 주석 | 해당 줄 위 한 줄 | 매직 넘버, 설계 결정의 이유 |

- 코드를 그대로 옮긴 문장, 값을 반복하는 주석(`이동속도 = 5`)은 쓰지 않습니다.
- **코드를 고친 커밋에서 주석도 같이 고칩니다.**

## 8. 작업 관리·버그 리포트

일정·작업 상태는 기존 노션 일정 보드에서 관리하고, 코드·에셋 변경은 GitHub PR에 연결합니다. 버그는 GitHub Issues에 기록하고 같은 내용을 별도 원본으로 중복 관리하지 않습니다.

작업 흐름은 **할 일 → 진행 중 → 리뷰/통합 → 완료**입니다. 막힌 작업은 막힌 이유·필요한 답·다음 확인 시점을 남깁니다.

| 작업 카드 필수 항목 | 적을 내용 |
| --- | --- |
| 목적·범위 | 플레이어에게 생기는 변화와 이번에 구현할 범위 |
| 담당·연결 상대 | 4장 배정에 따른 담당, 필요한 UI·로직·아트 인계 |
| 명세·데이터 | 최신 기획 위치, 요청/결과와 필요한 식별자 |
| 수정 경로 | 공유 씬·프리팹의 실제 경로와 현재 편집자 |
| 완료 기준 | 재현 가능한 동작·예외·확인 방법 |
| 결과·다음 작업 | 문서 커밋 또는 구현 PR, 확인 결과, 알려진 문제와 인계 내용 |

### 버그 리포트

GitHub **Issues**에 올리고, 고친 PR 본문에 `Fixes #번호`를 적습니다.

| 칸 | 내용 |
| --- | --- |
| 제목 | `[분야] 한 줄 요약` |
| 재현 방법 | 1, 2, 3 단계 |
| 기대 결과 / 실제 결과 | |
| 등급 | 막힘(진행 불가) · 중요 · 사소 |

## 9. 작업 완료·통합 기준

작업자는 자기 기능을 확인하고 결과를 구현 PR에 적습니다. 문서만 변경하면 커밋 본문·변경 기록 또는 작업 카드에 내용·링크 확인 결과를 남깁니다. 변경과 관계없는 항목은 해당 없음으로 표시하며, 검증하지 않은 것을 통과로 적지 않습니다.

- 최신 명세·데이터와 실제 동작이 맞고, 바뀐 규칙과 주석을 함께 갱신했다.
- 정상 동작뿐 아니라 취소·반복 입력·잘못된 대상·화면 재열기 등 해당 기능의 예외를 확인했다.
- 상태·타이머·저장을 바꾸면 화면 전환·다음 아침·저장 복구 후에도 연결과 값이 유지되는지 확인했다.
- 보상·금화·재료를 바꾸면 중복 처리와 이전 저장 정산의 재적용이 없는지 확인했다.
- 씬·프리팹 참조 누락, 컴파일 오류, 작업으로 생긴 콘솔 오류가 없고 `.meta`·출처를 포함했다.
- 구현은 UI·로직·아트 연결 상대에게 전달하고, 작성자 외 리뷰를 받았다. 합의된 문서 반영에는 추가 리뷰를 요구하지 않는다.

릴리스에서는 김언호가 대상 커밋·Unity 버전·빌드 결과를 기록하고 실행 파일을 확인합니다.
홍준우는 입력·화면 전환·표시를, 송예찬은 첫 영업 → 다음 아침 보고 → 재영업과 기획상 완료 기준을 확인합니다.
이기혁은 아트·초상·상태 레이어·회상 리소스의 누락과 표현을 확인합니다.
실행 빌드와 확인 결과가 갖춰진 뒤 마일스톤 태그를 붙입니다. 문서만 바꾼 작업은 링크·내용 대조로 확인하고 게임 실행 결과를 주장하지 않습니다.
