## 1. 저장소 구조

저장소 루트가 곧 Unity 프로젝트이고, 문서는 `Docs/`에 둡니다. 💡

```text
Project_DOB/
├─ Assets/
│  └─ _DOB/                 우리 게임 에셋 (외부 에셋과 섞이지 않게 분리)
│     ├─ 01.Scenes/
│     ├─ 02.Scripts/
│     ├─ 03.Prefabs/
│     ├─ 04.Art/            Models · Textures · Materials · VFX
│     ├─ 05.Animations/
│     ├─ 06.Audio/          BGM · SFX
│     ├─ 07.UI/
│     ├─ 08.Data/           ScriptableObject 데이터 (몬스터·재료·요리·종족·경제)
│     └─ 99.ThirdParty/     외부 에셋 (설치 경로를 고정하는 패키지는 예외)
├─ Packages/
├─ ProjectSettings/
├─ Docs/                    기획·명세·회의록·플레이 테스트 기록
├─ README.md                팀 규칙 (이 문서)
└─ CLAUDE.md                Claude 작업 안내 (이 README를 따르도록 연결)
```

- Unity는 `Assets` 밖의 폴더를 읽지 않으므로 `Docs/`가 빌드에 들어가지 않습니다.
- `Library/`, `Temp/`, `Logs/`, `UserSettings/`, IDE 파일은 `.gitignore`로 제외합니다. PC마다 다시 만들어지므로 처음 열 때 오래 걸리는 것은 정상입니다.

## 3. Git 규칙

### 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `main` | 제출·발표용. 직접 커밋하지 않음 |
| `dev` | 통합. 기능 브랜치를 PR로 합침 |
| `feature/이름-기능` | 개인 작업. 예: `feature/yechan-menu-resolver` |

- 기능 브랜치는 `dev`에서 만들고, 끝나면 `dev`로 **PR**을 엽니다. 💡 리뷰어 1명 확인 후 병합
- `main`에는 마일스톤마다 `dev`를 합칩니다. 💡 (알파 · 1차 테스트 · 제출)

### 커밋 메시지

```text
[분류] 무엇을 했는지 한 줄
```

| 분류 | 예 |
| --- | --- |
| `[사냥]` | `[사냥] 재료 근접 자동 습득 추가` |
| `[경영]` | `[경영] 메뉴 결정 동률 처리 수정` |
| `[UI]` · `[아트]` · `[사운드]` | `[UI] 정산 화면 골드 연출 추가` |
| `[기획]` · `[문서]` | `[기획] 직접 영업 수치 가안 반영` |
| `[설정]` · `[버그]` | `[설정] URP 품질 설정 정리` |

### 매일 지킬 순서

1. Unity를 열기 **전에** `git pull`
2. 작업 → Unity에서 저장
3. 커밋 → `git push` (작업 중이어도 그날 끝날 때는 자기 브랜치에 push)

- 에셋을 추가·이동·삭제하면 **`.meta` 파일도 함께** 커밋합니다. `.meta`가 빠지면 다른 사람 PC에서 참조가 끊깁니다.
- 충돌이 나면 혼자 덮어쓰지 말고 해당 파일 담당자와 같이 해결합니다.

## 5. 에셋 규칙 (Git LFS 없음)

LFS를 쓰지 않으므로 저장소 용량을 직접 관리합니다.

- GitHub는 **파일 하나가 100MB를 넘으면 push를 거부**합니다.
- 텍스처는 💡 최대 2048px. 큰 이미지를 여러 번 고쳐 올리면 그때마다 기록에 쌓입니다.
- 원본 작업 파일(`.psd`, `.blend` 등)은 저장소에 넣지 않고 공유 드라이브에 둡니다. 🔴 드라이브 링크
- 외부·무료 에셋은 `99.ThirdParty/`에 두고, 출처와 라이선스를 `Docs/에셋_출처.md`에 기록합니다.

### 이름 규칙 💡

| 종류 | 접두사 | 예 |
| --- | --- | --- |
| 모델 | `SM_` | `SM_Monster_Cabbage` |
| 텍스처 | `T_` | `T_Monster_Cabbage_Albedo` |
| 머티리얼 | `M_` | `M_Monster_Cabbage` |
| 프리팹 | `PF_` | `PF_Monster_Cabbage` |
| 애니메이션 | `A_` | `A_Player_Run` |
| 효과음 / 배경음 | `SFX_` / `BGM_` | `SFX_Pickup`, `BGM_Night` |
| 데이터(ScriptableObject) | `SO_` | `SO_Monster_Cabbage` |

- 영어 PascalCase와 `_` 구분을 씁니다. 공백과 한글 파일명은 쓰지 않습니다.

## 6. 코드 규칙

### 이름

- 클래스·메서드·프로퍼티: `PascalCase`
- private 필드: `camelCase` 💡 (`_` 접두사는 쓰지 않음)
- 인스펙터 노출은 `public` 필드 대신 `[SerializeField] private`
- 파일 하나에 `MonoBehaviour` 클래스 하나, 파일 이름과 클래스 이름을 같게

### 수치는 코드에 쓰지 않는다

몬스터 체력, 요리 가격, 보너스 같은 **기획 수치는 `08.Data`의 ScriptableObject**로 만듭니다. 기획 문서의 데이터 표와 1:1로 맞춰서, 수치를 바꿀 때 코드를 고치지 않게 합니다.

### 주석

| 종류 | 어디에 | 무엇을 |
| --- | --- | --- |
| 파일 헤더 | 파일 맨 위 | 역할 · 누가 호출하나 · 무엇을 호출하나 · 가진 상태 |
| `/// <summary>` | 공개 멤버, `[SerializeField]` 필드 | 무엇인지, 단위·범위 (값은 쓰지 않음) |
| 의사코드 | 흐름이 복잡한 함수만 | 처리 순서를 3~6단계로 요약 |
| "왜" 주석 | 해당 줄 위 한 줄 | 매직 넘버, 설계 결정의 이유 |

- 코드를 그대로 옮긴 문장, 값을 반복하는 주석(`이동속도 = 5`)은 쓰지 않습니다.
- **코드를 고친 커밋에서 주석도 같이 고칩니다.**

## 7. 기획 규칙

### 규칙은 두 층으로 쓴다

| 층 | 누구를 위한 것 | 형태 |
| --- | --- | --- |
| 플레이어 규칙 | 플레이어 | 한 문장, 수치·공식 없음 |
| 시스템 규칙 | 기획·프로그래밍 | 공식, 기준값, 동률·예외 처리 |

- 시스템 규칙은 플레이어 규칙을 **배신하지 않아야** 합니다. 플레이어 규칙대로 플레이한 사람이 가장 이득이어야 합니다.
- 공식은 숨기고 결과는 보여줍니다. 시스템 규칙마다 **"플레이어가 이걸 어떤 화면·연출로 아는가"** 를 함께 적습니다.
- 예외는 기본적으로 "아무 일도 안 일어나는" 쪽으로 정합니다.

### 수치와 문서

- 규칙·수치를 바꾸면 **기획 문서를 먼저** 고치고 변경 기록을 남긴 뒤 구현합니다.
- 테스트 전 수치는 💡 가안으로 표시하고, 플레이 테스트 결과로 확정합니다.
- 문서 기준 💡: 규칙·수치·명세는 이 저장소 `Docs/`가 기준, 노션은 GDD 개요·일정 보드·회의록 — 🔴 팀 확정
