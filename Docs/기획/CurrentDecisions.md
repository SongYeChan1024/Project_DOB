## 게임과 제작 범위

손님의 상태를 읽고 안전한 귀환을 위해 요리하는 식당 경영이다.
3D 쿼터뷰 운영 중 E로 손님을 맞이하고, 1인칭 응대 구도의 2D 초상·대사·아이콘으로 단서를 읽는다.
플레이어가 평문 대사에서 단서 표현을 찾아 클릭하면 그 말에 밑줄이 생기고 수첩에 손님별로 기록된다. 해당 위험 줄은 첫 발견 때 나타나며, 서로 다른 단서를 찾을 때마다 한 칸씩 찬다. 같은 표현을 다시 눌러도 칸 수는 유지된다. 독 단서의 클릭별 예시는 [첫 영업 연출안](콘텐츠/FirstServiceDirection.md)에 있다.

💡 **수첩 칸 계산 변경안** · 발견한 표현은 모두 사전에 남기고, 칸에는 이번 방문에서 확인한 위험 원인별 증감값을 한 번씩 합산한다. ‘점액’과 ‘따끔’이 같은 층 위험을 가리키면 독 1칸을 유지한다. 수인의 약점을 따로 찾으면 2칸, 사제의 가호까지 찾으면 1칸이다. 대사와 관찰 단서가 어떤 원인을 공개하는지는 [조건별 단서표](시스템/DialogueClueRules.csv)에서 검토한다.

주방 화면 가운데에 현재 조리도구를 두고 좌우에 요리도구를 배치한다. 플레이어가 재료와 양념을 직접 넣고 빼며 효과를 비교한 뒤 확정하면 6초 자동 조리한다.
기본 재료인 밀가루·감자·고기는 무한·무료이며, 금화·양념이 없어도 영업을 계속한다.
게임 오버 분기는 추가하지 않는다.

아침 귀환 보고 → 준비 → 영업 → 마감 → 다음 아침으로 이어진다.
동시 좌석 수와 하루 총방문 수는 분리한다.
💡 시작 3석·총방문 6명·화구 2개·영업 약 180초는 시험값이다.
마감은 새 접수를 닫고 접수한 주문을 마무리한다.
식사를 마친 손님은 계단 옆 방명록에 자기 사연과 맛 소감을 남긴다. 마지막 손님이 글을 다 쓴 순간 일일 정산을 시작한다.
💡 마지막 손님을 돌려보내면 방명록이 쓰이지 않으므로, 정산 조건을 「새 접수를 닫은 뒤 접수한 모든 방문이 끝난 상태(방명록 작성 완료 · 돌려보냄 · 미접수 귀가)」로 정의하는 안을 둔다. 첫날 튜토리얼에서도 돌려보내기를 허용하므로(노션 카드 01 E3) 튜토리얼에도 같은 조건을 적용한다(송예찬 제안 2026-11-24, 팀 합의 전, 김언호 상태 전이 확인).
🟡 돌려보내기 호감 −1의 대상이 메인 기획 4-1(단골만)과 4-8 호감 표(전 손님)에서 다르다. 「모든 손님이 guestId별 호감을 누적」 결정에 맞춰 4-8 기준(전 손님)을 제안하며 노션 원문 확인이 필요하다.
고정 설치 소품과 연결 좌석의 효과를 기본으로 하며 자유 배치·거리·방향·복수 중첩은 확장 범위다.

첫 검증은 1~2층, 최종 제공 목표는 5층·레시피 22개다.
안내 1명+병행 연습 2명과 다음 아침 → 하루 전환·보고·저장 → 임시 엔딩 → 5층·단골 확장 → 외부 플레이·빌드 검증 순으로 진행한다.
개발 기간은 제작 검증 후 재산정하며 예전 README의 11일을 고정 일정으로 적용하지 않는다.

## 튜토리얼 수정

새 게임 첫 방문부터 손님을 무작위로 정한다. 앞서 정한 이름·종족·직업·정답 요리를 방문 순서에 배정하지 않는다. 대사·외형·취향은 생성된 손님과 맞추고, 방명록과 다음 아침 보고에는 그 방문의 손님과 주문을 그대로 연결한다.
첫날 안내 1명 → 병행 연습 2명 → 아침 보고·양피지 독백, 첫 영업 목표 5~8분과 시작 마늘 2개는 기존 기준을 따른다. 특정 조합을 반복 확인할 때는 [손님 시험 데이터](시스템/FirstGuestsData.md)를 쓴다.
응대·재료 선택·수첩의 자동 조리 표를 「진행」으로 바꾼다.
T08·T10은 읽는 동안에도 조리가 완성될 수 있다고 안내한다.
확인 기준은 「잔여 4초에 응대 10초 → 응대 중 완성, 닫으면 접시 ready」다.
첫 양피지 독백과 그림은 카엘(A안) 기준이다.
대성공 예: 「그릇이 비었다. 돌아올 힘까지 담겼던 모양이다.」
단계 잠금·대사·드롭·체크포인트는 초안·시험값이며 구현 통과를 뜻하지 않는다.

## 관계·스토리·엔딩

방명록은 손님 이름별로 방문 순서대로 보여 준다. 같은 이름이 나와도 내부 기록은 손님의 `guestId`로 구분한다. 글을 쓸 때는 던전에 들어가기 전이므로 그날의 탐험 결과는 다음 아침 보고에서 알려 준다. 💡 글을 마치고 나갈 때 손님 머리 위에 맛 소감 이모티콘을 잠시 띄운다. 표정과 방명록 문구에는 같은 식사의 맛 반응을 쓴다.

음식이 입에 맞으면 호감이 오르고, 평범하면 유지하며, 싫으면 내려간다. 좋아하거나 싫어하는 맛이 하나도 없으면 기본 맛 점수 2다. 던전에서 음식이 도움이 됐다면 다시 찾아올 동기가 생긴다. 재방문 응대에서는 이전 식사를 떠올리는 말로 취향을 암시한다.

**손님 반응 추가 기획안** · 손님별로 기다린 시간을 보고 호감도 차감을 판정한다. 식후에는 음식이 그 손님의 입맛에 맞았는지로 입소문과 호감도를 각각 판정한다. 다음 아침에는 같은 방문의 실제 탐험 결과로 입소문과 호감도를 다시 판정한다. 음식 맛을 좋아했어도 귀환 때는 다른 반응이 나올 수 있다. 같은 식후 반응이나 같은 귀환 보고를 다시 열면 기록된 결과를 표시한다. 대기 차감 기준·횟수, 등급별 호감도 증감량과 입소문 발생 조건은 검토 중이다. [손님 반응 흐름도](플레이/Flowcharts/04-guest-reactions.png)

첫 재방문 검증은 튜토리얼 이후의 작업이다. 처음 플레이하는 사람이 방명록·아침 보고·재방문 대사를 보고 다음 접시에 남길 효과와 바꿀 맛을 자기 말로 설명하는지 확인한다. 🔴 아침 보고 대상, 보고 중 불러오기와 보상 중복 방지, 5층 구조 준비의 통과 조건과 부족한 준비를 보완하는 방법은 후속 결정이다.

모든 손님이 guestId별 호감을 누적한다.
단골이 되어도 과객 때 이름을 유지하고 [단골] 태그만 추가한다.
단골 자격과 개인 사연 배정은 분리한다.
같은 종족·직업의 A/B/C 후보가 모두 사용되어도 단골이 되며, 공용 단골 반응을 사용한다.
💡 호감 3 전환, 3·7·12 사연 해금은 시험값이다.
60개 이름·42개 사연 조각·270장면 구성은 유지한다.

5층은 사건 장소이며 던전의 마지막 층이 아니다.
생존·위치·접근 경로·장비·자기 처방과 도시락 준비를 검증하고 계단 출발로 이어진다.
5층 대성공만으로 엔딩을 열지 않으며 실패나 희귀 재료 획득을 필수 진행 관문으로 강요하지 않는다.
귀환 후 AfterReturn으로 전환해 금화·재료·설비·단골·열린 층을 유지하고 영업을 재개한다.
보고별 짧은 독백과 주요 양피지 편린의 최초 해금을 분리하고, 재생·생략으로 보상이나 필수 사실을 중복 처리하지 않는다.

## 일차 저장과 게임 진입 (2026.11.23)

저장은 일차 시작 스냅샷 기준이다. 일일 정산이 끝나면 효과를 한 번만 적용하고 일차를 넘긴 뒤 다음 날 시작 시점을 원자적으로 자동저장한다.
수동 저장은 언제든 가능하며 현재 일차 시작 시점 스냅샷을 별도 수동 슬롯에 저장한다. 쓰기 전 “불러오면 1일차 시작 시점부터 다시 시작합니다. 저장하시겠습니까?”(1일차 예시)로 확인하고, 취소하면 변화 없음, 저장 뒤에는 현재 플레이를 이어간다.
불러오기와 타이틀의 이어하기는 저장된 일차의 시작부터 시작하고 그날의 진행은 버린다. ESC 메뉴(이어하기·저장·불러오기·환경설정·끝내기)의 이어하기는 현재 세션을 재개하고 최근 자동저장의 일차와 날짜·시각을 표시한다.
타이틀에서 새 게임이나 이어하기를 선택하면 로딩 화면을 거쳐 게임 베이스로 진입한다. 베이스에 플레이어·카메라·입력·영업 진행을 두고, 식당 레벨(스폰 위치·좌석·주방)과 영업 UI는 각각 Additive로 불러온다. 프로토타입은 캡슐과 그레이박스를 쓴다.
현재 `main`은 `Title → Loading → Restaurant + Gameplay`로 진입한다. `Basement` 브랜치의 시험 영업은 타이틀, 게임 베이스, 식당 레벨, 영업 UI를 나눠 첫 손님과 일차 저장을 연결한다.

💡 **매니저 배치와 데이터 수명 제안** — 타이틀은 새 게임·이어하기 요청을 보내고, 게임 베이스는 새 게임의 1일차 기본값 또는 최근 유효한 저장 슬롯의 일차 시작값으로 영업을 연다. 영업 중 금화·재고는 담당 시스템이 관리하고, 게임을 다시 실행하면 저장 파일에서 복원한다. 현재 범위에서는 별도 매니저 씬이나 상주 데이터 싱글턴이 필요하지 않다. 세부 기준은 [메인 기획서의 코드 구조](MainPlanning.md#매니저-배치와-데이터-수명)에 둔다.

손님·방문·주문·보고·사실·처리 ID·난수 상태를 함께 보존한다.
자기 처방·왕복 위험·장비·도시락의 구체 검증값과 최종 대사는 작성이 필요하다.
수치는 Assets/_DOB/08.Data의 ScriptableObject에서 관리한다.

옛 웹 시제품 구현 문서의 2.4초·화구 1개·고정 단골·유한 기본 재료는 당시 기록이다.
현재 제작에는 이 문서와 MainPlanning.md를 사용한다. 문서 동기화가 웹 시제품 코드 변경을 뜻하지 않는다.
