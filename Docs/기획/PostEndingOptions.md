# 엔딩 이후 영업 방식 후보

> 최신 결정은 [CurrentDecisions.md](CurrentDecisions.md)가 우선한다.
> 카엘·모라·시에의 3인 파티와 엔딩 후 AfterReturn 영업 재개를 적용한다.
> 아래 A/B/C 비교·과거 변경 기록은 검토 경위를 보존한 것이다.

작성자: 송예찬 · 작성일: 2026.10.26

상태: 💡 비교·추천안. 사용자가 선택하기 전까지 어느 후보도 확정하지 않는다. 기존에 선택한 동기 ‘돌아올 힘을 남기지 않은 사람’과 고립 원인 ‘A. 무너져 분리된 구역’을 전제로 한다.

## 0 기획 의도

동료에게 돌아갈 준비를 마친 주인공의 변화가 엔딩 뒤에도 이어져야 한다. 식당의 성장과 손님 관계는 유지하고, 끝없이 깊어지는 던전으로 향하는 사람들의 귀환을 계속 돕는다.

| 후보 | 이야기 연결 | 필요한 개발 | 판단 |
| --- | --- | --- | --- |
| 💡 A. 함께 돌아온 뒤 다시 문을 연다 | 계단 출발 뒤 짧은 구조·귀환 후일담. 동료들은 안전한 곳에서 회복하고, 주인공은 식당으로 돌아온다. 처음에는 죄책감으로 시작한 일이 이제 스스로 선택한 일이 된다. | 기존 식당 씬, 출발·귀환 대사, 이야기 완료 상태, 이후 반응 교체. 구조는 직접 조작 없이 전달. 동료 직원·신규 모델 없이도 성립 | **추천.** 결말을 닫으면서 기존 경영 흐름을 이어갈 수 있음. 개발 부담 낮음 |
| 💡 B. 결말 직전의 식당으로 돌아간다 | 엔딩을 본 기록은 남기되 자유 영업은 출발 전 시점으로 돌아감. 필요할 때 결말 다시 보기 | 엔딩 감상 기록과 현재 이야기 시점을 분리하고, 되돌아온 시점 안내 | 개발 부담 가장 낮음. 다만 동료를 구하러 떠난 선택이 영업에 반영되지 않아 정서적 마무리가 약함 |
| 💡 C. 동료들이 가끔 들르는 식당 | 구조·귀환 후 회복한 동료들이 손님으로 방문해 함께 식사. 각자의 새 생활을 들려줌 | A안에 방문 데이터·대사·모델 또는 기존 임시 외형 재사용·재방문 조건 추가 | 후속 확장 후보. 소수의 대사 이벤트로 좁히면 부담을 줄일 수 있지만, A보다 인물 제작·검증 증가 |

💡 관리 대행자를 세워 주인공이 던전에 있는 동안 식당을 돌리는 방식은 이번 추천에서 제외한다. 새 직원·조작 주체·병행 시간 흐름을 설명해야 하기 때문이다. C안도 동료를 직원으로 자동 편입하지 않는다.

## 1 플레이어 규칙 — 추천 A안 💡

1. 현재 아침의 귀환 보고를 모두 확인하고 영업 준비 상태에서 출발을 선택한다. 영업 중에는 출발할 수 없다.
2. 도시락·자기 식사·경로·장비 준비가 검증되면 주인공이 계단을 내려간다. 구조 행동은 짧은 후일담으로 전달한다.
3. ‘돌아오는 길을 함께 건넜다’는 사실과 동료들의 회복을 확인하고 식당으로 복귀한다. 정확히 며칠이 흘렀는지는 표시하지 않는다.
4. ‘다시 문 열기’를 선택하면 기존 준비 → 영업 → 마감 → 귀환 보고 흐름을 이어 간다. 금화·재료·설비·단골·탐험 개방 상태를 유지한다.

💡 귀환 후 대사 예시: “돌아온 뒤에도, 식탁을 기다리는 사람은 있었다.” / “오늘은 누구의 돌아올 몫을 챙겨 줄까.”

💡 동료들이 살아서 돌아왔다는 결과는 보여 주되 구체적 장비·구조 장면·회복 기간을 임의 확정하지 않는다. 🔴 동료 인원·대사·구조 준비의 구체적 검증 기준은 기존 미정 항목과 함께 작성한다.

## 2 시스템 규칙 — 트리거·순서·예외 💡

- 진입 조건: `현재 보고 전부 확인 AND 영업 준비 상태 AND 현재 생존·위치 확인 AND 유효한 자기 처방·구조 계획 AND 엔딩 정책 선택`.
- 출발 확정 시 준비 스냅샷·소모 항목·연출 단계를 하나의 저장 단위로 기록한다. 비용은 한 번만 소모한다. 🔴 아직 없는 도시락 비용을 임의로 확정하지 않는다.
- `출발 → 귀환 후일담 → 영업 재개 가능`을 저장한다. 연출 중 종료하면 저장된 단계에서 이어지며 비용·보상을 중복 적용하지 않는다.
- 엔딩 완료 시 `storyPhase = AfterReturn`으로 바꾼다. ‘엔딩 봄’과 ‘후일담 확인’을 구분하여 복귀 전 영업 재개를 막는다.
- 재개는 기존 영업 준비 상태로 연결한다. 🔴 구조의 경과 시간은 미정이므로 부재 기간의 매출·지출·손님 탐험·부상 회복을 임의로 계산하지 않는다. 제안 범위에서는 귀환 보고가 남지 않은 안전한 경계에서 출발해 시점 충돌을 줄인다.
- 옛 파티 조사 임무의 새 배정을 종료한다. 수첩의 사실·확인한 장면은 남긴다. 미재생된 초기 죄책감 장면은 이후 시점에 맞는 반응으로 바꾸거나 생략 처리한다.
- 엔딩 이후 첫 ‘간신히’·부상은 그 손님의 상태를 살피는 대사로 처리한다. 동료들이 아직 갇혀 있다는 회상으로 되돌리지 않는다.
- 다시 보기는 연출만 재생한다. 금화·재료·날짜·현재 단계·보상에 영향을 주지 않는다.
- 6층 이후 실제 콘텐츠 제작·무한 위험 생성·새 직원·구조 미니게임을 엔딩 재개의 필수 작업으로 추가하지 않는다. 던전은 더 깊다는 세계관과 실제 제공하는 층 범위를 분리한다.

### 확인 기준

| 확인 상황 | 기대 동작 |
| --- | --- |
| 귀환 보고 또는 영업 손님이 남아 있음 | 출발 불가. 기존 흐름으로 먼저 정산 |
| 출발 버튼 연속 입력 / 연출 중 저장·재접속 | 비용·연출 진입 중복 없음 |
| 후일담 확인 후 영업 재개 | 기존 금화·재료·설비·단골·열린 층 유지 |
| 엔딩 이후 일반 귀환 부상 | 현재 손님에 대한 반응. 옛 파티 생존을 다시 미확인으로 바꾸지 않음 |
| 결말 다시 보기 | 게임 상태 변화 없음 |
| 엔딩 정책·자기 처방 기준 미설정 | 일반 영업은 가능. 정식 엔딩 출발은 잠금 |

## 3 데이터 💡

| 기획 명칭 | 변수명 | 타입 | 초기값 | 비고 |
| --- | --- | --- | --- | --- |
| 엔딩 이후 정책 | `postEndingPolicy` | enum | `AfterReturn` | 사용자 승인: 함께 귀환한 뒤 영업 재개. 자기 처방·장비·왕복 위험 기준은 가안 |
| 엔딩 연출 단계 | `endingSequenceStep` | enum | `NotStarted` | 출발·귀환·확인 완료 저장 |
| 엔딩 소모 처리 ID | `endingTransactionId` | string 또는 없음 | 없음 | 중복 소모 방지 |
| 영업 재개 가능 | `canResumeAfterEnding` | bool | false | 귀환 후일담 확인 뒤 true |
| 이후 이야기 단계 | `storyPhase` | enum | 기존 값 | A안 채택 시 `AfterReturn` 추가 |

Unity 구현 시 기획 설정은 Define의 ScriptableObject에 두고, 조건·판정은 System, 흐름·저장 연결은 Manager·Presenter, 입력·표시는 UI가 담당한다.

## 4 UI·피드백 💡

기존 3D 식당의 계단·조리대·출입문을 재사용한다. 짧은 대사와 빈 식탁에 다시 그릇을 놓는 연출만으로 복귀를 전달하는 안을 우선한다. 동료 전원의 모델과 별도의 구조 던전 씬은 필수가 아니다. 웹 시제품에서는 조작 확인용 텍스트를 사용하며 최종 UI·연출 확정 자료로 취급하지 않는다.
