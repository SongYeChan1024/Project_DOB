## 동시 손님과 상태 전이

- 💡 하루 입장 인원 = 열린 자리 수(3~6). 시작할 때 모두 입장한다. 각 손님은 독립적인 `visitId`, 자리, 레시피, 양념, 투입 재료, 완료 시각을 가진다.
- 💡 일반 첫날 보리·아멜·쥐를 우선한다. 이후 단골 2명을 우선하고 남는 자리는 과객으로 채운다. 방문 횟수가 적은 단골부터 순환한다. 🔴 원본의 확률적 등장 비중을 최종적으로 사용할지 결정 필요.
- `state.index`는 응대 대상을 고르는 선택 인덱스다. 진행 순번으로 쓰지 않는다. 실제 식당 안 손님은 `departed/declined`를 제외한 모든 방문이다.
- `waiting → cooking → ready → carrying → served → departed`. 조리 전 돌려보내기는 `waiting → declined`이며 기존 호감 감소 규칙을 적용한다.
- 같은 자리를 두 손님에게 배정할 수 없다. 조리 전에는 빈 자리로 이동할 수 있고 조리를 시작하면 고정한다. 배웅·돌려보내기 후 자리가 비워진다.
- 💡 화구 1개: 한 요리가 `cooking`일 때 새 조리 시작 차단. `ready` 음식은 화덕에 보관되므로 다음 요리를 시작할 수 있다.
- 💡 손에는 접시 1개만 들 수 있다. 소유자는 `carrying` 방문 ID로 결정한다. 선택 손님을 바꿔도 접시 소유자가 바뀌지 않는다. 다른 손님에게 판매·정산할 수 없다.
- 모든 손님을 배웅하거나 돌려보낸 뒤 마감한다. 조기 마감은 별도 확인 창을 거친다. 이미 조리 중·완성·운반 중인 음식이 있으면 차단한다. 아직 조리하지 않은 방문의 준비 재료는 소모하지 않고, 원본의 조기 마감처럼 별도 호감 패널티 없이 종료한다.
- 🔴 입장 간격, 추가 대기열, 인내심, 중도 이탈, 완성 음식 보관 한도·변질은 미정. 🟡 손님끼리 피해 걷는 이동은 미구현.

## 상태를 드러내는 첫 대사

1. 입장 시 피곤하면 피로 대사군을 우선한다.
2. 그렇지 않으면 실제 H에서 가장 큰 양수 위험의 대사군을 고른다. 양수 위험이 없으면 건강한 상태 대사를 사용한다.
3. 대사군별 변형을 고르고 `visit.opening/openingKey`에 저장한다. 같은 손님의 직전 대사와 같으면 다음 변형을 고른다.
4. 선택 전환·자리 변경·화면 재열기·저장 복원으로 다시 뽑지 않는다. 사람 이름에 상태 형용사를 붙이지 않는다.

💡 대사는 현재 상태와 위험 대비 필요를 알려 주는 초안이다. 🔴 최종 문체·표정·음성·처음 방문과 재방문별 말투는 미정. 목적지의 추가 단서와 호감 7의 두 단서 규칙은 유지한다.

## 저장 호환과 구현 파일

기존 `dob-3d-v1-*` 저장 키를 유지하고 `serviceVersion=4`를 추가한다. 이전 순차 진행 저장의 현재 인덱스 앞에서 `served`로 남아 있던 방문만 `departed`로 변환한다. 재고·금고·기존 호감·해금·보고 ID는 보존하며 소급 정산하지 않는다. 이전 버전은 양념 2칸이었으므로 `shelf`가 없는 저장은 2칸으로 복원한다. 새 일반 영업만 원본의 1칸에서 시작한다. 원본 2D HTML의 저장은 다른 키이며 이 버전으로 자동 가져오지 않는다.
