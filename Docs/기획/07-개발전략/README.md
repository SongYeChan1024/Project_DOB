## 7-2. 왜 3D인가

재설계안 「3D여야 하는 이유」의 두 가지(요리를 한다, 손님에게 맞는 자리를 선정해 배치한다)를 구체적인 설계로 옮긴다.

| 이유 | 설계 |
| --- | --- |
| 자리가 처방이다 | 자리의 효과는 난로, 창, 화분, 칸막이처럼 공간에 놓인 사물에서 나온다.<br>쿼터뷰로 한눈에 보이고, 자리를 늘릴 때 무엇을 놓을지가 처방 수단을 고르는 일이 된다 |
| 몸으로 단서를 읽는다 | 쿼터뷰 운영은 3D 동선으로, 응대는 2D 초상·직업 장비·컨디션·단서 레이어와 대사로 전달한다. |
| 동선이 곧 시간이다 | 입구, 자리, 카운터를 직접 걸어 다닌다.<br>누구에게 먼저 가고 무엇을 먼저 나를지가 경영 판단이 된다 |
| 던전이 식당 바로 아래에 있다 | 계단을 내려가는 손님, 붕대를 감고 돌아온 단골이 같은 공간에서 보인다 |

🟡 몸짓 단서는 애니메이션 비용이 든다.<br>
초기 구현에서는 머리 위 작은 효과(땀방울, 김)를 우선 검토하고, 애니메이션 적용 범위는 제작 여건을 보고 정한다.

### 3D라서 가능한 것

3D 쿼터뷰라서 할 수 있는 단서 · 규칙 · 연출 아이디어다.<br>
모두 제안 단계이며, 우선 구현 범위는 팀이 정한다.

| 아이디어 | 내용 | 쓰는 곳 |
| --- | --- | --- |
| 1. 손님 외형을 단서로 | E 응대 구도에서 종족·직업 기본 2D 초상과 상태 레이어를 관찰한다.<br>개인 취약점 5축은 그림·대사·아이콘으로 함께 알리고 체력 피로와 구분한다.<br>종족 약점과 개인 취약점이 같은 축이면 합산한다(예: 수인+기침 → 독 +2). | 추리 단서 (4-4). 3D의 강점을 가장 직접 살린다 |
| 2. 자리 소품 효과를 공간으로 | 첫 완성본은 고정 소품과 연결 좌석의 효과를 구매 전에 보여 준다.<br>위치·방향·인접 거리·복수 소품 중첩은 확장 명세로 남긴다. | 자리 처방 (4-5) |
| 3. 층계참 구조 보여 주기 | 손님은 위층 계단으로 들어오고, 식사 뒤 던전 계단으로 내려간다.<br>다음 날 결과에 따라 그을리거나 멀쩡한 모습으로 올라온다.<br>계단 아래에서 올라오는 빛 색으로 오늘의 이변을 예고한다 (3층 용암 균열은 붉은빛, 2층 곰팡이 동굴은 푸른 포자 안개) | 연출.<br>귀환 보고 (4-7), 오늘의 소식 (4-4) |
| 4. 단골이 남긴 물건으로 식당 꾸미기 | 단골 사연에서 받은 문장, 구급함, 광석, 열쇠, 지도를 식당에 실제로 놓는다.<br>식당이 손님들의 이야기로 점점 채워지는 게 눈에 보인다 | 스토리.<br>단골 사연 (3-3, 4-8) |

🟡 응대용 초상·표정·상태 레이어의 호환성과 제작량을 아트 담당이 검토한다.<br>
자유 배치·방향·거리·중첩은 확장 범위다.

## 7-4. 코드 구조 — 5계층

코드는 다섯 계층으로 나눈다(README 6장 개정안).<br>
아래 계층은 위 계층을 모르고, 계층 사이는 이벤트로 소통한다.<br>
기존 3계층(Data · Game · UI)에서 Data를 Define과 Utils로, Game을 System과 Manager · Presenter로 나눴다.

| 계층 | 하는 일 | 이 게임에서 |
| --- | --- | --- |
| 4 Manager · Presenter | 하위 계층을 조립하고 UI와 System 사이를 잇는다 | GameManager(하루 진행 · 기능 연결), 화면별 Presenter |
| 3 UI | 화면 표시와 입력만.<br>계산 없이 이벤트를 보낸다 | 대화창, 주방 카운터, 귀환 보고, 준비 화면 |
| 2 System | 게임 규칙 · 판정 · 상태 머신 | 위험 판정, 손님 흐름, 조리 타이머, 귀환 처리, 성장.<br>스토리 조건·단서·중복 방지 (4-10) |
| 1 Utils | 공용 도구와 전역 이벤트 버스 | EventBus, 난수 · 수학 도우미, 저장 |
| 0 Define | ScriptableObject 정의 · enum · 데이터 클래스 | 위험 축, 층 · 재료 · 레시피 · 양념 · 종족 · 직업 · 단골 데이터.<br>스토리 트리거·단서·요청·저장 상태 (4-10) |

- UI는 System을 모른다.<br>
대화창의 선택은 이벤트로 나가고, 판정 결과를 화면에 옮기는 일은 Presenter가 한다.<br>
UI 담당과 로직 담당이 서로의 파일을 고치지 않는다.

- 판정 엔진은 MonoBehaviour가 아닌 순수 C# 클래스로 만든다.<br>
주방의 효과 미리보기와 실제 판정이 같은 코드를 쓰므로 "보여 준 대로 일어난다"가 보장된다.

- GameManager는 하루 진행과 기능 연결을 조정한다. 금화·재고는 각각의 상태를 소유한 System이 변경한다.<br>
새 기능은 System에 클래스를 새로 만든다.

- 계층마다 asmdef(DOB.Define · DOB.Utils · DOB.Systems · DOB.UI · DOB.Manager)를 둬서 역참조를 컴파일 오류로 막는다.

### 매니저 배치와 데이터 수명

💡 현재 영업 범위의 설계 제안이다. 타이틀에는 시작 메뉴를, 게임 베이스에는 영업 진행을, 식당 레벨에는 좌석·주방 위치를, 영업 UI 씬에는 표시·입력을 둔다. 게임 베이스가 필요한 시스템과 화면을 연결한다. 예를 들어 주문창을 닫아도 주문과 조리 상태는 게임 베이스에서 유지된다.

| 시점 | 사용할 데이터 |
| --- | --- |
| 타이틀에서 새 게임 | 게임 베이스가 1일차 기본 금화·재고로 시작한다. |
| 타이틀에서 이어하기 · 게임 재실행 후 이어하기 | 최근 유효한 자동·수동 저장 파일에서 일차 시작 스냅샷을 읽는다. 씬 전환 중에는 시작값을 잠시 보관하고 게임 베이스가 받아 영업을 연다. |
| 영업 중 ESC에서 이어하기 | 현재 일차·금화·재고·주문 상태를 그대로 두고 일시 정지를 푼다. |

이 흐름은 별도 매니저 씬이나 전역 데이터 싱글턴 없이 구성할 수 있다. 추후 게임 베이스를 교체할 때 저장되지 않은 상태까지 이어야 한다면, 그 상태를 가진 객체 하나를 `DontDestroyOnLoad`로 유지하는 방식을 검토한다. 이 경우 생성 책임을 한 곳에 두어 씬 재진입 때 중복을 막는다. 게임 종료 후의 복구는 [일차 저장 기준](../09-승인과제작기준/README.md#저장-기준)을 따른다.

## 7-7. 대사 데이터 설계

대사량이 큰 제작 비용이다.<br>
일반 손님 반응은 프로토타입처럼 조각을 조합하고, 첫 결과·파티 표식·현재 질문과 답장·생존 방식·출발 장면은 트리거 ID에 연결된 원고로 관리한다. 🔴 최종 대사와 질문·동료별 상태는 작성 필요 (4-10).

| 조각 | 프로토타입 기준 수량과 예시 |
| --- | --- |
| 축별 단서 대사 | 축마다 3개.<br>함정: "[[함정]]이 많대.<br>눈치가 빨라야 해." |
| 오늘의 이변 문장 | 축마다 1개.<br>"바닥 틈의 [[열기]]가 오늘따라 거세다고 한다." |
| 맛 반응 | 맛 점수 0~4마다 1개.<br>"이거야! 딱 내가 원하던 맛이야." |
| 각오 한마디 | 부족 0~3마다 1개.<br>"든든하긴 한데… 뭔가 하나 모자란 느낌이야." |
| 귀환 한마디 | 결과 등급마다 3개, 가장 모자란 축 이름을 끼워 넣는다 |
| 단골 사연 | 조각 42개(종족 15 · 직업 18 · 뼈대 9)를 조합.<br>종족·직업 조합마다 후보 3개, 단골마다 3단계(💡 호감 9 · 21 · 36) |

원고의 `[[ ]]`는 클릭할 수 있는 단서의 범위를 지정한다. 대화가 열리면 평문으로 보이고, 플레이어가 찾아낸 표현에만 밑줄이 남는다.

## 7-8. 문제 발생 및 해결 방안

| 위험 | 대응 |
| --- | --- |
| 추리가 너무 쉽다 | 대사는 가장 큰 축 하나만 가리킨다.<br>나머지는 층 지식과 수첩으로 채워야 한다 |
| 추리가 너무 어렵다 | 사전 탭, 보고에서 원인 공개, 수첩 누적, 💡 호감 21 이상 단서 두 개 |
| 매번 같은 처방이 정답이 된다 | 오늘의 이변, 피곤, 돌발, 직업 보정이 날마다 위험을 바꾼다 |
| 재료가 떨어져 막힌다 | 기본 재료 무료·무제한으로 영업 재개를 보장한다.<br>양념·던전 재료·개량은 경제 선택으로 유지하며 게임 오버·빚·재시작 비용을 새로 추가하지 않는다. |
| 자리 처방이 판정을 망가뜨린다 | 자리 효과를 돌발 보험 역할로 바꾸는 대안 (4-5) |
| 3D일 이유가 약하다는 피드백 | 7-2의 네 가지를 그레이박스 단계에서 먼저 보여 준다 |

## 7-9. 팀 구성 및 역할

팀 역할은 팀 노션 「팀 구성 · 협업 규칙」을 따른다.

송예찬 (기획 / PM): 기획서 · 노션 문서, 판정 수치 · 데이터 입력, 대사 원고, 일정 관리, 플레이 테스트 진행

김언호 (프로그래밍 · TA): 플레이어 이동 · 상호작용, 손님 흐름(입장 → 대화 → 자리 → 조리 → 서빙 → 계단), 판정 엔진 이식, 조리 타이머

홍준우 (프로그래밍 · UI/UX): 정보 표시·입력, 대화·주방·귀환 보고·준비 화면·수첩 연결.<br>
하루 전환·저장 데이터 계약은 김언호와 함께 정하고 통합 책임자를 명시한다.<br>
이펙트·사운드는 첫 루프 통합과 분리한다.

이기혁 (아트 / 연출 / 모델 수정): 식당·자리 소품 3D 에셋, 운영용 외형·응대용 2D 초상·상태 레이어, 카엘(A안) 기준의 일러스트·양피지 회상·컷씬 연출.
