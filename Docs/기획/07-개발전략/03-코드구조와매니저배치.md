# 코드 구조와 매니저 배치

[← 7. 개발 전략](README.md) · [메인 기획서](../메인기획서.md)

코드 규칙의 기준은 저장소 README 6장이다. 이 문서는 그 구조가 이 게임의 기능에 어떻게 대응하는지 정리한다.

## 다섯 계층과 이 게임의 대응

| 계층 | 하는 일 | 이 게임에서 |
| --- | --- | --- |
| 4 Manager · Presenter | 하위 계층을 조립하고 UI와 System 사이를 잇는다 | GameManager(하루 진행·기능 연결), 화면별 Presenter |
| 3 UI | 화면 표시와 입력만. 계산 없이 이벤트를 보낸다 | 대화창, 주방 카운터, 귀환 보고, 준비 화면 |
| 2 System | 게임 규칙·판정·상태 머신 | 위험 판정, 손님 흐름, 조리 타이머, 귀환 처리, 성장. 스토리 조건·단서·중복 방지(후속) |
| 1 Utils | 공용 도구와 전역 이벤트 버스 | EventBus, 난수·수학 도우미, 저장 |
| 0 Define | ScriptableObject 정의·enum·데이터 클래스 | 위험 축, 층·재료·레시피·양념·종족·직업·단골 데이터. 스토리 트리거·단서·저장 상태(후속) |

- 아래 계층은 위 계층을 참조하지 않는다. 독립 기능 사이의 알림은 이벤트 또는 Presenter 중재를 쓰고, 같은 기능 안의 계산·조회까지 전역 이벤트로 바꾸지 않는다(README 6장).
- UI는 System을 모른다. 대화창의 선택은 이벤트로 나가고, 판정 결과를 화면에 옮기는 일은 Presenter가 한다.
- 판정 엔진은 MonoBehaviour가 아닌 순수 C# 클래스로 만든다. 주방의 효과 미리보기와 실제 판정이 같은 코드를 써서 "보여 준 대로 일어난다"를 보장한다.
- GameManager는 하루 진행과 기능 연결을 조정한다. 금화·재고·손님·주문의 실제 변경은 각 상태를 소유한 System이 한다.
- 계층별 asmdef(DOB.Define · DOB.Utils · DOB.Systems · DOB.UI · DOB.Manager)로 역참조를 컴파일 오류로 막는다.

> 이전 문장 “계층 사이는 이벤트로 소통한다”는 README 6장 개정(이벤트는 독립 기능 사이 알림에만) 전 표현이어서 위처럼 바꿨다.

## 매니저 배치와 데이터 수명

💡 설계 제안이다. 타이틀에는 시작 메뉴를, 게임 베이스에는 영업 진행을, 식당 레벨에는 좌석·주방 위치를, 영업 UI 씬에는 표시·입력을 둔다. 게임 베이스가 필요한 시스템과 화면을 연결한다. 예를 들어 주문창을 닫아도 주문과 조리 상태는 게임 베이스에서 유지된다.

| 시점 | 사용할 데이터 |
| --- | --- |
| 타이틀에서 새 게임 | 게임 베이스가 1일차 기본 금화·재고로 시작한다. |
| 타이틀에서 이어하기 · 게임 재실행 후 이어하기 | 최근 유효한 자동·수동 저장 파일을 읽는다. 자동 저장은 일차 시작 상태, 수동 저장은 누른 시점의 상태다(2026-11-25). 씬 전환 중에는 시작값을 잠시 보관하고 게임 베이스가 받아 영업을 연다. |
| 영업 중 Esc에서 이어하기 | 현재 일차·금화·재고·주문 상태를 그대로 두고 일시 정지를 푼다. |

이 흐름은 별도 매니저 씬이나 전역 데이터 싱글턴 없이 구성할 수 있다. 추후 게임 베이스를 교체할 때 저장되지 않은 상태까지 이어야 한다면 그 상태를 가진 객체 하나를 `DontDestroyOnLoad`로 유지하는 방식을 검토한다. 이 경우 생성 책임을 한 곳에 두어 씬 재진입 때 중복을 막는다.
게임 종료 후의 복구는 [제작 순서와 저장 기준](../09-승인과제작기준/02-제작순서와저장기준.md)을 따른다. 기능별 총괄 Manager 분담은 [구현 기능과 총괄 Manager 구성안](../../개발/FeatureManagerMap.md)이 기준이다.

## 핵심 구현 기능

| 번호 | 기능 | 계층 | 내용 |
| --- | --- | --- | --- |
| 1 | 판정 엔진 | System | 프로토타입 엔진을 C#으로 옮긴다. 위험·효과·부족·전리품·호감 계산. 돌발은 스토리 이후 안건으로 보류한 차후 확장(2026-11-25) |
| 2 | 데이터 | Define + 08.Data | 층·재료·레시피·양념·종족·직업·단골·대사·개량을 ScriptableObject로 둔다. |
| 3 | 손님 흐름 | System | 입장 → E 응대 → 자리 → 재료 투입·양념·확정 → 6초 자동 조리 → 서빙 → 식후 반응·방명록 → 계단. 영업 중 시간은 Esc 일시 정지 메뉴에서만 멈춘다(FeatureManagerMap F2). 대화·수첩·재료 선택 중에도 손님 시간과 조리가 흐른다. |
| 4 | 대화·주방 화면 | UI + Presenter | 첫 루프 필수 UI: 2D 초상·대사·알려진 위험·효과 비교·재고·주문 표시. 상세 장식은 이후 보완 |
| 5 | 아침 보고·준비 화면 | UI + Presenter | 첫 루프 필수 UI: 귀환 원인·보상·수첩·준비 선택. 결과 확정과 재진입 중복 방지를 함께 검증 |
| 6 | 하루 진행·저장 | Manager + Utils | 준비 → 영업 → 마감·정산 → 다음 아침. 확정 귀환 보고와 처리 ID를 저장해 중간 종료 시 누락·중복을 막는다. 스토리 사실·대기열 저장은 후속이다. |
