# 개발 연결·상태 관리 지침

작성자: 송예찬 · 2026-10-31

게임 규칙·수치·시간 정책은 [최신 기획 결정](../기획/CurrentDecisions.md)을 따른다.

## 1. 기존 담당 배정과 전달 경계

| 담당 | 책임 | 다른 담당자에게 전달할 것 |
| --- | --- | --- |
| 송예찬 | 기획·PM·수치·원고·완료 기준·플레이 테스트 | 명세 위치, 시험 데이터, 기대 결과, 우선순위 |
| 김언호 | 이동·상호작용·판정·손님/주문/조리 상태·기술 통합 | 요청/결과 정의, 상태 조회, 거절 사유, 저장·복구 연결 |
| 홍준우 | UI/UX·입력·정보 표시·화면 Presenter | 화면 입력 요청, 화면 열기/닫기 알림, 결과 표시와 연결 확인 |
| 이기혁 | 식당·소품·운영용 외형·2D 초상·상태 레이어·회상 연출 | 에셋·외형 프리팹, 레이어 규격, 원본·출처, 임포트 확인 |

하루 전환·저장 데이터 계약은 두 개발자가 함께 정한다.
김언호는 상태·복구·기술 통합, 홍준우는 화면·입력·표시 연결을 담당한다.
같은 씬·프리팹을 고쳐야 하면 현재 편집자와 실제 파일 경로를 작업 카드에 적어 순서대로 인계한다.
역할별 작업물을 실행 씬에 통합하는 책임과 에셋 자체의 제작 책임을 구분한다.

## 2. 조리 한 건의 연결 예시

| 순서 | 처리 주체 | 하는 일 |
| --- | --- | --- |
| 1 | UI | 사용자가 재료·양념을 고르면 입력 조합을 표시한다. 실제 재고를 바꾸지 않는다 |
| 2 | 화면 Presenter | visitId·orderId·레시피/재료 ID를 포함한 조리 시작 요청을 전달한다 |
| 3 | 주문/조리 System | 주문 상태·필요 수량·실재고·화구를 검사하고, 유효하면 재료를 한 번 소비해 조리를 시작한다 |
| 4 | System → Presenter → UI | 시작 결과 또는 거절 사유, 남은 시간·완성 상태를 전달·표시한다 |
| 5 | 조리 System | 조리 시계로 완료를 판단하고 해당 주문을 ready로 바꾼다. 화면이 닫혀 있어도 처리한다 |
| 6 | 상호작용 → System | 지정 주문의 접시를 픽업·서빙한다. 접시 주인과 중복 입력을 검사한다 |

거절된 요청은 금화·재고·주문을 부분적으로 바꾸지 않는다.
완료 표시는 System의 실제 상태를 읽으며, UI 타이머가 별도로 완료를 판정하지 않는다.
요청과 결과에는 같은 주문 식별자를 사용한다. 그 사이 선택 손님이 바뀌어도 다른 주문을 갱신하지 않는다.
클릭 중복 차단은 UI 조작 편의이고, 실제 중복 처리 방지는 상태를 소유한 System에서 보장한다.

## 3. 호출과 이벤트

| 경우 | 연결 방식 |
| --- | --- |
| UI에서 게임 동작 요청 | UI 입력 → Presenter → 해당 System |
| 게임 동작 처리 결과 | 결과 반환 또는 완료 이벤트 → Presenter → View |
| 독립 기능의 상태 변경 알림 | 이벤트 또는 연결 담당의 중재. 필요한 ID·결과만 전달 |
| 같은 기능 내부의 계산·조회 | 명시적인 메서드·데이터 전달. 전역 이벤트로 우회하지 않음 |
| 순수 계산 | 입력을 받아 결과 반환. UI·씬·전역 상태에 의존하지 않음 |

아래 계층에서 Manager·Presenter·UI를 역참조하지 않는다.
전역 이벤트 버스는 영속 상태 저장소가 아니다. 화면을 다시 열면 현재 상태를 조회하여 표시한다.
이벤트가 과거에 한 번 발생했는지 여부만으로 저장 복구·완료 상태를 추정하지 않는다.
이벤트 타입·요청/결과 DTO는 Define, 전달 도구는 Utils에 두어 UI와 System이 서로를 참조하지 않게 한다.
직접 연결 객체는 인스펙터 또는 조립 단계에서 전달하고 Find 계열로 임의 검색하지 않는다.

## 4. 구독·초기화·종료

- 활성화 범위 구독은 OnEnable/OnDisable, 인스턴스 수명 구독은 초기화/종료처럼 같은 수명 범위에서 연결·해제한다.
- 해제할 수 없는 임시 람다 구독과 중복 초기화를 피한다. 반복 열기·닫기에도 콜백이 한 번만 실행되어야 한다.
- System·저장 데이터 복구를 준비한 뒤 Presenter를 연결하고, View에 현재 상태를 전달한다.
- UI가 먼저 열리면 미초기화 상태를 표시하고 입력을 막는다. 준비되지 않은 값을 정상값으로 처리하지 않는다.
- 비동기 처리 후 화면·주문이 여전히 유효한지 확인한다. 닫힌 화면이나 이미 처리된 주문을 다시 갱신하지 않는다.
- 종료·씬 전환에서는 구독·진행 중 작업·참조를 정리한다. 새 씬이 이전 화면의 이벤트를 받지 않게 한다.

## 5. 시간과 상태

대화·수첩·재료 선택 중에는 영업 시간·손님 입장·이동은 정지하고 조리는 진행한다.
일시 정지 메뉴·아침 보고·회상 중에는 조리도 멈춘다.
정지 사유는 원인별로 관리한다. 대화를 닫았다는 이유로 열린 수첩·일시 정지 메뉴의 정지까지 해제하지 않는다.
구체적인 시계·저장 표현 방식은 구현 계약에서 정하되, Time.timeScale 하나로 서로 다른 시간 정책을 표현하려 하지 않는다.

기준 ScriptableObject를 실행 중 손님·주문 상태로 덮어쓰지 않는다.
이름·개인 취약점·사연 배정은 guestId에, 주문·접시·조리 진행은 visitId·orderId에 연결한다.
UI 선택값과 실제 확정값을 구분하고, 화면 재열기만으로 소비·추첨·보상을 재실행하지 않는다.

## 6. 저장·다음 아침·보고

저장 경계의 세부 기준은 기획의 검토 상태를 유지한다. 이 지침으로 새 자동 저장 시점을 확정하지 않는다.
개발 계약에는 손님·방문·주문·보고·이야기 사실·처리 ID·난수·시간 정책을 함께 다룬다.
이미 정산된 보고는 다시 보거나 불러와도 금화·재료·호감·사연 보상을 재적용하지 않는다.
귀환 보고 확정과 화면 표시를 구분하며, 주요 장면 재생·생략도 상태 보상을 중복 처리하지 않는다.
저장 오류를 정상 저장처럼 표시하지 않고, 실패 사유와 복구 가능한 상태를 전달한다.

## 7. 인계와 검증 예시

| 변경 | 확인할 동작 | 담당 확인 |
| --- | --- | --- |
| 조리 | 연속 확정 시 한 번 소비, 주문 전환 뒤에도 접시 주인 유지 | 김언호·홍준우 |
| 시간 정책 | 잔여 4초에 대화 10초면 완료. 일시 정지 중에는 진행하지 않음 | 김언호·홍준우 |
| 개인 취약점 | 동일 guestId로 재방문·단골 전환·복구 후 유지, 표시와 실제 판정 일치 | 김언호·홍준우, 송예찬·이기혁은 데이터/표현 확인 |
| 귀환 정산 | 보고 재열기·재접속으로 보상과 호감이 늘어나지 않음 | 김언호·홍준우 |
| 초상·레이어 | 종족·직업·컨디션·취약점 조합이 가려지지 않고 대사·아이콘과 일치 | 이기혁·홍준우 |
| 릴리스 | 첫 영업 → 다음 아침 → 재영업, 저장 복구, 실행 빌드 확인 | 김언호 통합, 홍준우 화면, 송예찬 플레이 기준, 이기혁 리소스 |

테스트는 변경한 책임과 위험에 맞게 선택한다.
순수 판정·중복 정산·저장 복구처럼 반복 검증이 필요한 부분은 자동 검사를 검토하고, 화면·참조·아트는 실제 실행으로 확인한다.
문서만 바꾼 작업에는 게임 실행 검증을 요구하거나 실행한 것으로 기록하지 않는다.
