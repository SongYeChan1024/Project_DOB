## 기능별 기획과 구현

첫 본영업 루프의 완료 기준은 1층 손님을 응대하고 2일차 아침 보고·준비를 거쳐 다시 영업을 여는 것이다. 1\~2층의 성장과 밸런스는 그다음 검증 범위다. 5층·레시피 22개, 단골 이야기와 엔딩 이후 영업은 확장 목표다.

### 손님이 정해지면 어떤 대사가 나오는가 · F3·F4·F11

1. **인물과 방문을 만든다.** 현재 main은 이름 60개, 종족 5종, 직업 6종의 목록에서 각각 균등 추첨한다. 완성 기획에서는 입장·대기 중인 손님과 단골의 이름을 제외한 후보에서 뽑고, 후보를 소진하면 전체 이름을 다시 허용한다. 재방문자는 이름과 손님 ID를 유지하고 새 방문 ID를 받는다. 같은 종족에서도 여섯 직업이 모두 나올 수 있다. 기획상 이름·종족·직업은 손님 ID에 남고 목적지·컨디션·선택한 대사는 이번 방문 ID에 남는다. 현재 main은 목적지를 1층으로 두고 신규 손님만 만든다.
2. **종족과 직업을 위험에 반영한다.** 목적지의 기본 위험에 그날의 이변, 종족 약점, 피로, 개인 취약점을 더하고 직업 보정을 적용한다. 독·열·냉기·어둠·체력·함정 여섯 축을 각각 계산하며 최종 위험의 최솟값은 0이다. 이 값은 대화를 열기 전에 정해진다. 현재 main의 입장 경로는 방문 호감 0과 이변 없는 1층을 사용한다. 생성기에서 지원하는 이변과 단골 조건은 별도 입력이 있어야 대사에 반영된다.
3. **무엇을 말할지 고른다.** 합산 결과가 가장 큰 양수 축을 고른다. 동률이면 방문 생성 때 한 축을 추첨한다. 그 축을 높인 원인 하나를 추첨하고, 그 원인에 연결된 원고 변형 중 한 편을 뽑아 방문에 보관한다. 양수 축이 없으면 “별일 없을 거야.”처럼 위험 표현이 없는 대사를 쓴다. 호감 21 이상에서 둘째 단서를 주는 시험안은 다른 양수 축의 원인을 먼저 고른다. 없으면 같은 축의 다른 원인을 고르고, 후보 원인이 하나뿐이면 한 문장으로 끝낸다.
4. **플레이어가 증거를 찾는다.** 대사는 처음에 평문이다. 클릭해 발견한 표현은 모두 밑줄로, 초상에서 찾아낸 특징은 관찰 표시로 남긴다. 수첩에는 각 원인의 보정값을 방문당 한 번만 합산한다. 응대 창을 다시 열면 같은 대사와 발견 기록이 나온다. 실제 위험은 플레이어가 몇 개를 찾았는지에 따라 바뀌지 않는다.

| 종족 · 위험을 높이는 특징 | 직업 · 위험을 줄이는 장비나 행동 |
| --- | --- |
| 인간은 종족 보정 없음. 수인 독 +1, 엘프 열 +1, 드워프 함정 +1, 하플링 체력 +1. | 사제 독 −1, 마법사 열 −1, 도적 함정 −1, 전사 체력 −1, 광부 어둠 −1, 궁수 냉기 −1. |

**예시 · 1층 슬라임 숲으로 가는 수인 사제**　층의 독 +1, 수인의 예민한 코 +1, 사제의 가호 −1이므로 실제 독은 1이다. 이 손님의 체력 위험도 1이어서 독·체력 중 어느 축을 말할지는 추첨으로 정해진다. 이번 방문에서 독 축과 층의 점액 원고가 뽑혔다면 손님은 “슬라임 점액이 튀면 따끔하더라.”라고 말한다.

| 이 방문에서 발견한 것 | 화면에 남는 표시 | 수첩의 독 |
| --- | --- | --- |
| 아직 단서를 찾기 전 | 평문 대사 | 미확인 · 현재 화면은 점선 |
| ‘슬라임 점액’ | 첫 표현에 밑줄 | 1칸 |
| 같은 문장의 ‘따끔’까지 | 두 표현에 모두 밑줄. 둘은 같은 층의 점액을 가리킨다. | 1칸 유지 |
| 코를 감싸는 몸짓 | 수인의 독 약점 관찰 표시 | 2칸 |
| 목에 건 성표 | 사제의 독 보정 관찰 표시 | 1칸 |

## 입소문으로 다음 영업의 손님 수 정하기 · F10

### 손님 한 명의 방문 호감 계산

**방문 호감 변화 = 대기 점수 + 입맛 태그 두 개의 합 + 탐험 결과 점수.** 식후에는 맛 소감을 보여 주고, 파견한 손님은 귀환 결과가 나온 뒤 이번 방문의 합계를 한 번 반영한다.

| 항목 | 점수 |
| --- | --- |
| 대기 | 남은 대기 점수 0\~2점. 0점에서 서빙을 받으면 입맛·탐험 판정을 이어 간다. |
| 입맛 | 두 태그를 각각 채점한다. 맞으면 +1, 틀리면 −1이므로 둘 다 틀림 −2, 하나만 맞음 0, 둘 다 맞음 +2다. |
| 탐험 | 대성공 +2, 성공 +1, 실패 −1, 대실패·부상 −2다. 기존 등급표의 ‘간신히’는 실패, ‘부상’은 대실패에 해당한다. |

**대기 0점에서 입맛 두 개를 모두 놓친 첫 손님**　기존 개인 호감은 0이고, 음식 맛에서 −2점을 받았다.

| 탐험 결과 | 이번 방문 합계 | 재방문에 미치는 영향 |
| --- | --- | --- |
| 대성공 | 0 − 2 + 2 = 0 | 방어가 맛의 감점을 만회한다. 재방문 후보에 남는다. |
| 성공 | 0 − 2 + 1 = −1 | 개인 호감이 음수여서 재방문을 거절한다. |
| 실패 | 0 − 2 − 1 = −3 | 개인 호감이 음수여서 재방문을 거절한다. |
| 대실패·부상 | 0 − 2 − 2 = −4 | 부상으로 쉬고 호감도 음수다. 예정 명단에서는 한 명만 제외한다. |

기존 개인 호감이 있는 손님은 이번 방문의 증감을 기존 값에 더한다. 예를 들어 호감 5인 손님의 방문 점수가 −1이면 개인 호감은 4다. 재방문하려는 손님도 부상 중에는 쉰다. 한 방문의 호감 변화는 최소 −4점(대기 0 + 입맛 −2 + 대실패 −2), 최대 +6점이다. 본영업에서 손님을 돌려보내면 그 방문의 호감 변화는 최솟값인 −4점으로 한 번 확정한다. 음식이나 탐험 점수는 추가로 합산하지 않는다. 예를 들어 개인 호감 5인 손님을 돌려보내면 1이 된다. 직접 돌려보낸 방문의 −4점은 그날 일일 정산에서 반영한다. 대기 시간을 넘겨 스스로 떠난 방문도 본영업에서 방문 호감 −4점으로 한 번 처리하며, 대기 0·입맛·탐험 점수를 따로 더하지 않는다(2026-11-24 송예찬, [이슈 #30](https://github.com/SongYeChan1024/Project_DOB/issues/30#issuecomment-7125508653)). 대기 이탈의 −4점을 같은 일일 정산에서 반영하는지는 아직 명시되지 않았다.

### 입소문 추가 인원과 실제 방문 수

**전날 몇 명을 응대했는가.** 한 사람의 방문 호감은 최대 +6이다. 전날 손님 수를 N, 이번 영업에서 그 손님들이 얻은 방문 호감 점수의 합을 S라고 하면 하루 최대는 6N, 절반 기준은 3N이다. 세 명이면 최대 18점·기준 9점, 네 명이면 최대 24점·기준 12점이다.

**💡 입소문 증원 제안.** 하루 최대 점수의 60%·75%·85%·100%에 도달할 때마다 다음 영업에 한 자리씩 추가한다. 50%는 기준점이고 첫 증원은 60%다. 85%와 100%는 세 명일 때 16점에 +3명, 만점 18점에 +4명을 유지하도록 고른 제안값이다. 각 문턱은 필요한 점수를 올림한다. 도달한 문턱의 개수가 추가 인원이다. N이 0이면 추가도 0명이다.

| 다음 영업 입소문 추가 | 전날 3명 · 최대 18점 | 전날 4명 · 최대 24점 |
| --- | --- | --- |
| +0명 · 60% 미만 | 10점 이하 | 14점 이하 |
| +1명 · 60% 이상 | 11\~13점 | 15\~17점 |
| +2명 · 75% 이상 | 14\~15점 | 18\~20점 |
| +3명 · 85% 이상 | 16\~17점 | 21\~23점 |
| +4명 · 100% | 18점 | 24점 |

세 손님이 모두 +6이면 18점으로 +4명이 된다. 세 명이 도달할 수 없는 19·20점 구간을 삭제했다. 네 손님이 합계 20점을 얻으면 20/24이므로 +2명이다. 새 비율을 적용하면 기존 3인표와 달라지는 점수는 11점(0명→+1명)과 14점(+1명→+2명)이다.

**실제로 몇 명이 오는가.** 기본 손님 수는 1일차 본영업에 3명으로 시작한다. 매 영업을 열 때 현재 식당의 성장 단계를 반영해 기본 손님 수를 정한다. 그날의 예정 인원 = 현재 성장 단계의 기본 손님 수 + 전날 호감으로 얻은 입소문 추가 인원(0\~4명). 예를 들어 기본 20명까지 성장하면 결석 반영 전 예정 인원은 20\~24명이다. 단계별 인원과 해금 조건은 밸런스 검토 항목이다. 예정 명단을 만든 뒤 ① 방어가 부족해 던전에서 다쳐 휴식 중인 손님, ② 개인 누적 호감이 마이너스가 되어 재방문하지 않는 손님을 제외한다. 두 사유가 겹쳐도 같은 손님 ID는 한 번만 센다. 예정에 없던 손님은 빈자리를 만들지 않는다. 그날의 이변은 해당 층의 위험을 바꾸는 조건이다. 손님의 단서를 놓쳤더라도 음식과 자리의 방어 효과가 실제 위험을 덮으면 부상 결석이 생기지 않는다. 결석은 실제 탐험 결과와 개인의 재방문 의사로 판정한다.

**예시.** 전날 네 손님의 방문 점수가 +6, +6, +2, −1이면 합계는 13점이다. 최대 24점의 60%에 못 미쳐 입소문 추가는 0명이다. 식당이 아직 기본 3명 단계라면 다음 영업에는 3명이 예정된다. +2를 받은 손님은 대기 +2, 입맛 +2, 대실패 −2로 호감이 올랐어도 부상으로 쉰다. −1을 받은 첫 손님은 대기 0, 입맛 −2, 탐험 성공 +1로 호감이 음수가 되어 재방문을 거절한다. 두 손님이 모두 다음 예정 명단에 있었다면 두 자리가 비고, 빈자리를 보충하지 않는 안에서는 한 명이 온다.

**부상 휴식과 재방문 거절.** 기존 기획은 부족 합 3 이상이면 부상·이틀 휴식이다. 휴식 중인 손님도 귀환 보고를 처리하고, 이후 올 예정인 날에만 명단에서 빠진다. 개인 호감 표시 범위는 0\~36이므로, 💡 이번 방문 증감을 더한 개인 호감이 0 미만이면 0으로 제한하기 전에 거절을 기록하는 안을 제안한다. 예를 들어 기존 5에서 −2면 3이므로 이 조건으로는 결석하지 않고, 기존 1에서 −2면 −1이라 거절한다. 누적 개인 호감이 0 미만이 된 손님은 이후 영구히 재방문하지 않는 방향이다(2026-11-24 송예찬 의견, [이슈 #30](https://github.com/SongYeChan1024/Project_DOB/issues/30#issuecomment-7125508653)). 방문 손님 수에 최댓값이 없어 새 손님은 계속 생길 수 있다는 판단이며, 송예찬이 팀 의견을 요청한 상태다. 새 손님이 계속 생길 수 있다는 것과 그날 예정 명단의 결석 자리를 당일 새 손님으로 보충하는 것은 별개이며, 당일 결원 보충 여부는 아직 정하지 않았다.

💡 입소문 합 S에는 개인 누적 호감의 상·하한을 적용하기 전 이번 방문 점수를 사용하는 안이다. 예를 들어 누적 36인 단골도 좋은 식사로 얻은 +6을 입소문에 기여할 수 있다. 전날 손님 수 N에는 대기 이탈한 손님을 포함하고, 그 방문의 −4점을 합 S에 한 번 더한다(2026-11-24 송예찬, 패널티로 봄). 직접 돌려보낸 손님을 N에 넣을지는 사용자 답변을 기다리는 중이며, 남은 쟁점은 이 하나다.

### 데모 확정 사양 · 하루 12명 이상 서빙 → 마감·정산 → 엔딩

영업 시작 때 식당 성장·입소문·결석을 반영해 그날 받을 손님을 정한다. 엔딩 지표는 **한 본영업일에 실제로 서빙을 완료한 서로 다른 손님의 수**다. 0일차 연습, 돌려보낸 손님, 음식을 받기 전에 대기 이탈한 손님은 집계에서 제외한다. 매 영업일 0명부터 세며 같은 손님의 같은 날 서빙은 한 번만 센다.

12명째에 도달해도 남은 손님을 계속 응대한다. 모든 방문이 끝나면 영업을 마감하고 그날의 정산창을 연다. 실제 서빙이 12명 이상이면 **정산창 확인 후 데모 엔딩**으로, 11명 이하면 다음 아침의 귀환 보고와 영업 준비로 넘어간다.

| 그날 영업에서 일어난 일 | 정산창 확인 후 |
| --- | --- |
| 12명 중 1명을 돌려보내고 11명에게 서빙했다. | 다음 일차로 넘어간다. 돌려보낸 손님은 방문 호감 −4점이다. |
| 13명 중 1명을 돌려보내고 12명에게 서빙했다. | 데모 엔딩을 보여 준다. |
| 13명에게 모두 서빙했다. | 13번째 손님까지 응대해 영업을 마치고 데모 엔딩을 보여 준다. |
| 어제 11명, 오늘 1명에게 서빙했다. | 오늘 실적은 1명이다. |

**엔딩 후 이어하기.** 데모 완료 슬롯에서는 엔딩을 본 일차의 시작 상태를 복원한다. 그 하루를 다시 플레이하고 마감·정산하면 해당 플레이는 끝난다. 재플레이에서 서빙 인원이 달라져도 다음 일차로 진행하지 않는다. 일차 시작의 금화·재고와 당일 명단을 복원해 지난 플레이의 수입·호감이 이중으로 누적되지 않도록 한다.

**후속 버전.** 스토리는 데모 완성 후 남은 시간에 따라 구현한다. 스토리를 추가한 버전에서는 이어하기로 다음 일차에도 계속 영업할 수 있도록 확장한다.
