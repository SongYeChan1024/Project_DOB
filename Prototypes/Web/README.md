💡 기획 검증용 시제품. 확정된 게임 사양이나 Unity WebGL 빌드가 아니다. 제공된 원본의 시장·레시피·수첩·가게·귀환·마감 화면과 칠판 미술을 기준으로 다시 구성하고, 영업 중 3D 이동·동시 응대·조리·서빙을 연결했다. 원본 HTML은 유지했다.

## 실행

설치 없이 `dist/restaurant-offline.html`을 Chrome에서 연다. 스크립트·미술·폰트를 외부 서버에서 가져오지 않는다. Three.js 라이선스 전문은 HTML 내부와 별도 `THREE-LICENSE.txt`에 포함했다.

- **영업 시작**: 원본 초기 경제(50g·기본 재료·양념 1칸)로 1층에서 시작. 동시 손님 3명(개량 후 최대 6명) → 마감 → 다음 아침 귀환 보고.
- **5층 조사부터 체험**: 5층과 재료·설비가 열린 별도 시험 저장. 스토리를 빨리 검토하는 용도.
- **단골 사연부터 체험**: 별도 저장. 보리 호감 2·아멜 6·솔 11에서 실제 식사→다음 아침을 거쳐 3·7·12 사연 해금을 확인한다. 이전 단계 사연은 시험용으로 기록됨.
- **저장한 영업 / 시험 이어하기**: 모드마다 다른 저장 슬롯. 손님 이름·재료·진행·보고 처리 여부 유지.
- 각 동작 뒤 브라우저에 저장한다. 파일 위치·브라우저·localhost 실행이 달라지면 저장 공간이 다를 수 있다. 저장 실패 시 하단에 안내하며, 메뉴에서 JSON 백업을 받을 수 있다. 🟡 JSON 불러오기 기능은 아직 없다.

WASD / 방향키로 이동하고, 가까운 물건·손님 앞에서 E를 누른다. 화면의 방향 버튼을 누르고 있어도 이동한다. 물건이나 장소 버튼을 멀리서 누르면 금색 원으로 목적지를 표시한다. 드래그로 시점 회전, 휠로 확대. 준비·보고·마감은 원본처럼 넓은 독립 화면이다. 영업 중 좁은 창에서는 조작 패널이 식당 아래에 배치된다. WebGL을 사용할 수 없는 환경에서는 이동 거리 제한 없이 장소 버튼으로 영업 흐름을 검토할 수 있다.

💡 이동 검증 배치: 가로 16 × 세로 14인 식당에 6자리를 유지했다. 조리대·화덕은 뒤쪽 벽에 붙이고, 주방과 테이블 사이에 주름 커튼 두 구간을 배치했다. 가운데와 양옆에 통로를 남겼다. 가구·커튼·벽은 통과할 수 없고, 커튼 너머에서 상호작용할 수 없다. 이동 속도 3.8/초, 반경 0.28, 상호작용 거리 1.35는 웹 시험값이다.

## 검토 순서

1. 손님의 장비·귀/수염·키·자세를 보고 상태를 관찰한다. 💡 외형 구분용 임시 모델이며, 텍스트 패널도 함께 제공한다.
2. 자리 가까이에서 E로 안내하면 층과 위험 단서를 듣는다. 조리 전에는 자리를 바꿀 수 있다.
3. 벽 붙임 조리대에서 전용 화면을 열고 도구에 필수 재료를 하나씩 넣는다. 양념은 1칸(선반 개량 후 2칸), 조리 완료 후 화덕에서 E로 해당 손님의 접시를 집는다.
4. 접시를 들고 손님 가까이로 이동해 E로 내어 준다. 맛 반응으로 새 취향을 알아내고, 수첩의 손님 기록에서 다시 확인한다. 마감 뒤 다음 아침 귀환 결과를 확인한다.
5. 결과에서 위험·효과·부족 합계를 비교한다. 시장 구매·화덕 개량·자리 해금 후 영업을 반복한다.
6. 5층 손님의 첫 보고로 표식과 연락 틈을 얻는다. 수첩에서 ‘현재 질문 전달’과 ‘외부 경로 조사’를 요청한다.
7. 다음 5층 손님의 보고를 받는다. 사실은 즉시 저장되지만 장면은 💡 하루 한 개씩 순서대로 확인한다.
8. 계단의 ‘엔딩 A안 시험 설정’을 켜면 임시 출발 기준을 검토할 수 있다. 생존 단서·지도·위치 장면·시험 계획·자기 식사·보급비를 모두 갖춘 뒤 출발한다.
9. 짧은 귀환 후일담을 보고 같은 저장의 영업을 계속한다. 층 해금·설비·재료·골드·손님을 유지하고 구조 조사는 종료한다.

## 코드 구조

팀의 5계층 제안을 웹에서 검증하기 위해 다음처럼 분리했다. Unity 이식 시 기획 수치는 ScriptableObject에 옮긴다.

| 계층 | 파일 | 책임 |
| --- | --- | --- |
| Define | `src/define/data.js`, `reference.json`, `room.js`, `taste.js`, `relationships.js`, `regulars.json`, `service.js` | 💡 수치·레시피·외형 이름·장면・배치・취향 규칙 정의 |
| Utils | `src/utils/runtime.js` | 이벤트 버스·난수·저장·텍스트 처리 |
| System | `src/system/rules.js`, `story.js`, `movement.js`, `taste.js`, `greeting.js` | 영업 상태 전이·위험/맛 판정·재고·정산·사건 조건·이동 충돌/근접 검사 |
| UI | `src/ui/scene.js`, `roomScene.js`, `input.js`, `panels.js`, `relationshipPanels.js`, `cookingPanel.js`, `fantasyTools.js`, `originalArt.js`, `style.css` | 3D 표현·화면 표시·입력 의도 전달. 보상 계산 안 함 |
| Manager / Presenter | `src/main.js` | 입력→시스템→저장→화면 연결, 귀환 이벤트 발행 |

보고 ID·방문 ID·손님 ID를 따로 보존한다. 귀환 정산 저장 후 사건을 발행하며, 이 사이에 종료되면 다음 로드에서 보고를 재전달한다. 시스템과 사건 처리 모두 같은 ID의 중복 적용을 막는다. 새 연락 요청을 맡은 손님을 돌려보내면 다음 영업에 재배정한다. 실제 날짜가 흘러도 재료나 생존 시간이 자동으로 줄어들지 않는다.

맛 판정은 기존 V0.3 원고 4-6절의 규칙을 복원했다. 기본 2 + 좋아하는 태그당 1(최대 2) − 싫어하는 태그 포함 시 2를 0–4로 제한한다. 중복 태그는 한 번만 센다. 판매가는 `반올림(레시피 기본값 × (0.6 + 0.2 × 맛 점수)) + 양념 개수`다. 맛 3 이상이면 미발견 선호 태그 하나를, 싫어하는 맛이 포함되면 해당 비선호를 알아낸다. 맛 3 이상으로 다치지 않고 귀환하면 💡 35% 확률로 재료 보너스 1개를 받는다. 맛은 위험 부족 합계에 영향을 주지 않는다. 단골은 귀환 결과와 맛을 합산해 호감을 올리며, 상세 규칙은 [단골 호감·사연 명세](../../Docs/기획/RegularRelationships.md)에 기록했다.

고정 단골의 취향은 기존 6명 데이터로 유지한다. 과객의 취향은 첫 생성 시 정하고 guestId와 함께 유지한다. 💡 종족별 선호 기본값을 쓰며 인간은 두 태그를 무작위로 고른다. 비선호 한 개는 선호와 겹치지 않게 뽑는다. 기존 저장에는 없는 취향·위치 필드만 보충하고, 들고 있는 접시와 이동 위치도 저장한다. 이전 배치의 가구 안에 저장된 위치는 조리대 앞 안전 지점으로 복구한다.

V0.3은 이전 저장의 무작위 손님·진행 중 식사·정산 완료 내역을 보존하고, 다음 영업부터 고정 단골을 추가한다. 이미 정산한 보고에 호감을 소급 적용하지 않는다. 단골 이름과 우연히 같은 과객이 있어도 ID를 분리한다. 사연의 지도·열쇠는 주인공의 구조 사건 조건을 대신하지 않는다.

V0.4의 원본 비교·동시 손님·재료 투입·상태 대사·저장 호환은 [상세 명세](../../Docs/기획/PrototypeV04ServiceCooking.md)에 기록했다. 장작 돌화덕·무쇠 솥·무쇠 팬·나무 볼은 💡 시제품 도구 배정이다.

## 소스 수정·빌드

Node.js 22 이상과 pnpm 11 환경에서 이 폴더를 작업 디렉터리로 사용한다.

```powershell
pnpm install --frozen-lockfile
pnpm test
pnpm build
pnpm start
```

서버 주소는 `http://127.0.0.1:4173`이다. 소스 수정 뒤 다시 빌드하고 새로고침한다. 서버는 현재 터미널에서 Ctrl+C로 종료한다. `tools/polish-source.mjs`는 JavaScript를 읽기 편하게 정리하는 선택 도구다. 기존 웹 원형의 데이터 재추출은 `tools/import-reference-data.mjs`를 사용하지만, 지정된 로컬 원본 경로가 있어야 한다.
